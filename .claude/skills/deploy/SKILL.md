# Выкатка на прод

Устройство контура — три env-файла, nginx, отличия prod-стека — в
`.claude/rules/deploy.md`. Здесь только порядок действий и то, обо что
спотыкаются.

## Правило, которое старше техники

**На стенд сама, на прод по просьбе.** Коммит и пуш идут в конце задачи сами,
и стенд подхватывает их из своего crontab — смотреть свежее глазами он для
того и заведён. Прод выкатывается только когда об этом попросили: на том
конце живая школа с чужими данными. Это правило про **прод**, и путать
контуры тут дороже всего.

**Прод тоже подтягивает себя из crontab — и это правила не отменяет.** Он
следит за веткой `production`, а она сама не двигается: пока её не
передвинули, опрос каждые пять минут не делает ничего. Просьба выкатить и
есть движение этой ветки. `main` прод не смотрит.

## Порядок

```bash
./push-deploy.sh "текст коммита"     # коммит + пуш + деплой + проверка сайта
./push-deploy.sh --deploy-only       # ничего не коммитить, только раскатать
```

Скрипт сам проверит, что вы в корне репозитория, на `main` и что в рабочем
дереве нет секретов, — `git add -A` иначе утащил бы их в коммит. Ветку
`production` он двигает сам, до ssh.

Флаги: `--deploy-only`, `--no-verify` (не проверять сайт), `--skip-env` (не
трогать `.env.prod`).

## Из облачной сессии и с телефона

Ssh-ключ есть только на ноутбуке, но выкатка к нему больше не привязана.
Контуры подтягивают ветки сами, а ветки двигаются через GitHub:

```bash
./scripts/ship.sh              # влить свою ветку в main  => стенд, до 3 мин
./scripts/ship.sh --prod       # и выкатить на прод       => прод,  до 5 мин
```

Работает везде, где есть `git`, — в облачной сессии в том числе. Ветку двигает
`gh` серверной операцией, а если его нет или он не авторизован — обычным
`git push`; и то и другое только перемоткой. Реализация одна: `push-deploy.sh`
с ноутбука зовёт этот же скрипт.

**Разрешение спрашивается про каждый запуск.** Это то же правило, что про
живые запросы в Anthropic, и по той же причине: на том конце живая школа с
чужими данными, а человек в момент запуска смотрит в другую сторону.

- «доделай и выкати на прод», «унеси на стенд» — просьба про этот запуск, это
  разрешение;
- «делай что нужно», «доведи до конца», включённый режим без вопросов —
  **не** разрешение. Работа доводится, ветка пушится, дальше человеку
  говорится, что готово, и называется команда;
- ранее выданное разрешение соседней задачи не переносится.

**Догадка «раз просили доделать, значит подразумевали выкатить» — это и есть
та ошибка, от которой правило.** Ветку в `main` слить без просьбы тоже нельзя:
это делает вашу работу общей и увозит её на стенд.

Чего `ship.sh` не умеет — возить `.env.prod`: файл вне git. Меняли набор
переменных — нужен ноутбук (`./scripts/sync-env.sh prod`), и об этом надо
сказать человеку, а не выкатывать «как есть».

## Перенести боевую базу на стенд

Когда смотреть надо на настоящие данные, а не на посев. Ssh нужен к обоим
контурам, и идёт всё **через ноутбук**: ключа между серверами нет.
Устройство и грабли — в `.claude/rules/deploy.md`, «Боевую базу на стенд
возят руками».

Адреса: прод `leobreslav@194.67.111.40:~/lesson-tracker` (база `lessons`),
стенд `leobreslav@194.67.119.42:~/apps/lesson-tracker` (база
`lessons_staging`). Ниже `C` — это
`docker compose --env-file .env.prod -f docker-compose.prod.yml`.

```bash
B=~/backups/transfer-$(date +%F)

# 1. дамп прода — с --no-owner --no-acl, иначе упрётся в чужую роль
ssh <прод> "mkdir -p $B; cd ~/lesson-tracker && \$C exec -T db \
  pg_dump -U lessons -d lessons --no-owner --no-acl | gzip > $B/prod-lessons.sql.gz"

# 2. довезти через ноутбук и сверить md5
scp <прод>:$B/prod-lessons.sql.gz .   &&   scp prod-lessons.sql.gz <стенд>:$B/

# 3. НА СТЕНДЕ: страховочный дамп цели — до всего остального
cd ~/apps/lesson-tracker
$C exec -T db pg_dump -U lessons_staging -d lessons_staging --no-owner --no-acl \
  | gzip > $B/staging-before.sql.gz

# 4. погасить backend: он держит соединения, DROP SCHEMA встанет насмерть
$C stop backend

# 5. снести схему (не --clean) и залить
$C exec -T db psql -U lessons_staging -d lessons_staging -v ON_ERROR_STOP=1 \
  -c "DROP SCHEMA public CASCADE;
      CREATE SCHEMA public AUTHORIZATION lessons_staging;
      GRANT ALL ON SCHEMA public TO public;"
zcat $B/prod-lessons.sql.gz | $C exec -T db psql -U lessons_staging \
  -d lessons_staging -q -v ON_ERROR_STOP=1

# 6. поднять backend — миграции идут при старте, и им есть куда идти:
#    прод стоит на production и отстаёт от main, на котором стенд
$C start backend
```

Проверка после: `showmigrations --plan | grep -c '^\[ \]'` даёт ноль, а
`School.objects.count()` — школу с боевым названием, не «Тестовую».

**Страховочный дамп цели — первый шаг, а не последний.** Его снимают до
того, как что-то погашено: если он не снялся, дальше идти нельзя, и `set -e`
в цепочке это обеспечивает.

**После переноса вложения битые** — бакеты R2 у контуров разные, — и на
стенде лежат чужие персональные данные. `--reseed` их сотрёт.

## Обо что спотыкаются

- **Скрипту нужен терминал — но только когда набор переменных менялся.**
  `.env.prod` синхронизируется **до** выкатки, и при расхождении скрипт
  спрашивает `[y/N]`; без TTY `read` падает с «ввод прерван». Обход через
  `script -qec` с `printf 'y'` на вход **не работает**: проверено — процесс
  простоял одиннадцать минут на вопросе, ничего не выкатив, и выяснилось это
  только по тому, что на сервере не появилось ни резервной копии, ни новой
  переменной.

  Если переменные не менялись, скрипт не спрашивает ничего. Если менялись —
  шаг env делается руками, теми же действиями, что и скрипт: копия
  `.env.prod.bak.<дата>` с `chmod 600` (хранить три последние), `scp`,
  `chmod 600`, сверить `sha256sum` с локальным файлом. Дальше
  `./push-deploy.sh --deploy-only --skip-env` проходит без вопросов.

  Из сессии Claude Code проще попросить пользователя выполнить
  `! ./push-deploy.sh …` — так вопрос задаётся в его терминале.
- **Перед выкаткой — зелёный полный прогон на GitHub, а не на этой машине.**
  Смотреть надо прогон **того коммита**, который поедет. Красный или ещё
  идущий — ждём, а не выкатываем; на ноутбуке полный набор для этого больше
  не гоняется (он там вдвое дороже и занимает машину). Правило и замер — в
  `CLAUDE.md`, «Какие тесты гонять и когда».

  **Ждут одним `gh run watch`, а не опросом `gh run list`.** Замер за девять
  дней: `list` вызывался 101 раз против 19 `watch` — по пять опросов на
  каждое ожидание, и каждый стоил круга модели в 15 секунд сверх самой
  команды. `watch` блокируется и возвращается сам; повторять его и
  перепроверять `list` не надо.

  **А чаще всего ждать не надо вовсе.** Ожидание нужно, только когда прод
  двигают прямо сейчас. Обычный порядок другой: влили в `main`, взялись за
  следующее, а `--prod` пришёл отдельной просьбой — к тому времени прогон
  давно кончился, и проверка сводится к одному взгляду на тот самый коммит:

  ```bash
  gh run list --commit "$(git rev-parse origin/production)" --limit 1
  ```
- **Правка nginx применяется не всегда.** `git pull` меняет файл заменой, а
  bind-mount держит inode: контейнер до конца жизни видит прежний конфиг.
  `deploy.sh` сверяет sha256 с содержимым контейнера и пересоздаёт его только
  при расхождении — обычная выкатка nginx не трогает. Если правка конфига «не
  доехала», смотреть надо сюда.
- **Миграции идут при старте контейнера** (`migrate --noinput`), отдельно
  запускать не нужно.
- **Выкатили движением ветки, а `.env.prod` меняли — фронт соберётся со
  старым.** Опрос на сервере возит только код; env-файл лежит вне git и
  приезжает с ноутбука (`./scripts/sync-env.sh prod`). Порядок: сначала env,
  потом ветка. `VITE_GOOGLE_CLIENT_ID` вшивается в бандл на сборке, так что
  проверять надо бандл, а не файл.
- **«Двинул ветку, а ничего не произошло»** — смотреть на сервере
  `tail -20 ~/.prod-autodeploy.log`. Опрос отказывается работать молча ровно
  в двух случаях, и оба он пишет в лог: контур не назвался прод'ом и дерево
  стоит не на `production`.
