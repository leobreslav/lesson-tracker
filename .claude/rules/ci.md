## Проверка на GitHub — питон и узловые

`.github/workflows/tests.yml` гоняет **тот же docker compose**, а не
собранную рядом «нативную» установку: второй способ запустить те же тесты
однажды разошёлся бы с первым, и узнали бы мы об этом по зелёному CI при
красном ноутбуке.

На каждый пуш любой ветки и на каждый пул-реквест идут две работы:

| работа | что в ней |
|---|---|
| `python` | сторожа-скрипты, потом `manage.py test` в контейнере |
| `node` | `npm test` в контейнере — тесты клиентской логики |

Сторожа-скрипты — `test-guard-anthropic-spend.py`, `test-prod-autodeploy.sh`,
`test-ship.sh`, `test-check-login-door.sh` — идут секундами и без контейнера:
`scripts/` в контейнер не монтируется. Стоят они в CI, а не только на
ноутбуке, потому что каждый стережёт то, что портится молча в обе стороны:
регулярка сторожа трат, автовыкатка прода, перенос веток, замок на дев-дверь.

Браузерных тестов в проекте нет — ни в CI, ни на ноутбуке, ни ночью; решение
принято 25 сентября 2026. Вёрстку и экраны проверяют глазами на dev-сервере.

### Дверь перед продом

**Прод (`production`) двигается только на коммит, у которого `python` и
`node` на GitHub зелёные, и только по явной просьбе человека.** Смотреть надо
прогон **того самого** коммита, который поедет: зелёное на ноутбуке ничего не
говорит о том, что уехало в `main`, — там мог оказаться чужой коммит.

**Ждут одним `gh run watch`, а не опросом `gh run list`**, и ждут только
когда прод двигают сейчас. Замер за девять дней: выкатка стоила 1.9 часа, из
них 72 минуты — ожидание CI, и `list` вызывался 101 раз против 19 `watch`.
Опрос дешёвой командой стоит не своих секунд, а круга модели в 15 секунд на
каждый вызов. Готовый прогон проверяется одним запросом по коммиту:

```bash
gh run list --commit "$(git rev-parse origin/production)" --limit 1
```

### `-T` и чистый клон

`docker compose run` на раннере зовётся с `-T`: терминала там нет, и без
флага compose спотыкается о «the input device is not a TTY». Локально флаг не
нужен — и не ставится, потому что с ним пропадает цвет и посекундный вывод.

Раннер начинает с чистого клона без единого ключа, то есть ровно с того, с
чего начинается облачная сессия. Поэтому первым шагом каждой работы стоит
`scripts/dev-env.sh` — без `.env` compose не поднимет ничего. Поломку
«сторож пустоты падает без ключей R2» такой прогон нашёл бы сам, и в этом
главная его ценность помимо зелёной галочки.

**Правило шире одного случая: чистый клон — это и раннер, и облачная
сессия.** Всё, что «работает, потому что уже лежит на диске» (`node_modules`,
`.env`, собранный образ), в обоих не работает. Локально зелёное такого не
ловит по определению; ловит либо CI, либо прогон с временно убранным
каталогом.

`package-lock.json` обновляется без установки пакетов на хост:

```bash
cd frontend && docker run --rm -v "$PWD:/app" -w /app --user "$(id -u):$(id -g)" \
  node:22-alpine npm install --package-lock-only
```
