## Боевая конфигурация

`docker-compose.prod.yml`, переменные в `.env.prod` (шаблон —
`.env.prod.example`; сам файл в проекте не лежит, см. ниже про три
env-файла). Первое развёртывание на сервер описано в
[DEPLOY.md](../../DEPLOY.md), последующие обновления — `./push-deploy.sh "текст
коммита"` с ноутбука: он коммитит, пушит, двигает ветку `production`,
запускает `deploy.sh` на сервере по ssh и проверяет, что сайт отвечает 200.
Флаги: `--deploy-only` (только раскатать), `--no-verify` (без проверки сайта)
и `--skip-env` (не трогать `.env.prod`). Перед стартом скрипт проверяет, что
мы в корне репозитория, на ветке `main` и что в рабочем дереве нет секретов —
`git add -A` иначе утащил бы их в коммит. На самом сервере всё то же делает
`./deploy.sh`.

Ноутбук при этом больше не единственная дверь: прод стоит на ветке
`production` и подтягивает её сам. Это отдельный раздел ниже, и читать его
надо до того, как понадобится выкатить не с этой машины.

### Кто хозяин .env.prod

Главная копия — **на ноутбуке, вне репозитория**: у прода
`~/secrets/lesson-tracker.env.prod`, у стенда `~/secrets/lesson-tracker.env.staging`
(пути меняются `DEPLOY_ENV_FILE` и `STAGING_ENV_FILE`). В git файл попасть не
может, значит, на сервер он приезжает копированием, а раз копирование
одностороннее, у файла должен быть **один хозяин**: иначе перенос однажды
затрёт правку, сделанную на сервере. Поэтому на серверах его руками не
редактируют вовсе, а `push-deploy.sh` отказывается работать, если локальный
файл лежит внутри репозитория.

Правило это долго действовало только для прода — перенос жил внутри
`push-deploy.sh`, — а файл стенда правился прямо на сервере. Стоило это
получаса на двух открытых `nano` над одним файлом и вопроса «а какая копия
теперь правильная». Теперь возит оба `scripts/sync-env.sh`, и
`push-deploy.sh` зовёт его же:

```bash
./scripts/sync-env.sh prod
./scripts/sync-env.sh staging --yes   # без вопроса, для скриптов
```

Реализация **одна намеренно**. Второй перенос рядом с первым — это две
копии одного правила, а расхождение между ними значит затёртый ключ на
боевом сервере: замечают такое в день, когда что-нибудь перестаёт пускать.

Синхронизация идёт **до** `deploy.sh`: сборка фронта читает оттуда
`VITE_GOOGLE_CLIENT_ID`. Сравниваются sha256; при расхождении показываются
только **имена** появившихся и исчезнувших переменных — значения не
печатаются ни при каких обстоятельствах, там пароль базы и токены R2.
Дальше подтверждение, копия `.env.prod.bak.<дата>` на сервере (хранятся три,
и они в `.gitignore` — иначе `deploy.sh` счёл бы дерево грязным), `chmod 600`
и сверка контрольных сумм после копирования. Нет локального файла —
предупреждение и пропуск шага, а не отказ: контур мог не заводиться на этой
машине.

Что где лежит и не разъехалось ли — `./scripts/check-secrets.sh`: отпечатки
по пяти контурам, значений не печатает.

### Прод стоит на ветке `production`, а не на `main`

Сервер выкатывает себя сам — `scripts/prod-autodeploy.sh` в crontab, раз в
пять минут:

```
*/5 * * * * /home/leobreslav/lesson-tracker/scripts/prod-autodeploy.sh
```

Вывода строка не перенаправляет намеренно: скрипт всё, что хочет сказать,
пишет в `~/.prod-autodeploy.log` сам, а молчание в stdout значит, что cron
не пришлёт письма на каждый тик. Дерево на сервере при этом обязано стоять
на `production` (`git checkout -B production origin/production`) — иначе
скрипт откажется работать и скажет об этом в лог.

Следит он **не** за `main`. Он следит за отдельной веткой,
которая сама никуда не двигается. Пока её не передвинули, опрос каждые пять
минут не делает ничего.

**Это не автовыкатка, и путать их дорого.** Стенд действительно выкатывается
сам после каждой задачи: он для того и заведён. Прод — нет. Решение выкатить
осталось человеческим, сменилось только место, где оно принимается:

| | было | стало |
|---|---|---|
| где решают | ноутбук с ssh-ключом | `github.com`, `gh`, любая машина |
| чем | `./push-deploy.sh` | передвинуть `production` |
| что делает сервер | принимает ssh | сам ходит за кодом, как и раньше |

Ради чего разводили. Ключ от боевой машины лежал ровно на одном ноутбуке, и
выкатка была к нему привязана. Облачная сессия, телефон, чужая машина —
ничего этого не могли не потому, что им не доверяют, а потому, что у них нет
ключа; а положить ключ туда — значит завести ему копии.

Почему опрос, а не GitHub Actions или вебхук — та же причина, что у стенда,
и на боевом контуре она весомее: обоим пришлось бы **пустить снаружи
внутрь**. Actions — ssh-ключ секретом в репозитории плюс открытый вход
раннерам GitHub; вебхук — слушающий эндпоинт с проверкой подписи. Опрос не
требует ничего: наружу ходит сам сервер, туда же, куда и так ходит за кодом.

Выкатывается это так:

```bash
git push origin main:production          # с ноутбука
gh api repos/leobreslav/lesson-tracker/git/refs/heads/production \
    -X PATCH -f sha="$(git rev-parse origin/main)"   # или так, без git
```

либо кнопкой на `github.com` — PR из `main` в `production`. Дёрнуть прод, не
дожидаясь тика, можно тем же опросом, разбуженным руками — это не второй
способ выкатывать, а тот же самый:

```bash
ssh <прод> '~/lesson-tracker/scripts/prod-autodeploy.sh'
```

#### Двигает ветки один скрипт — `scripts/ship.sh`

```bash
./scripts/ship.sh              # влить свою ветку в main  => стенд
./scripts/ship.sh --prod       # и выкатить на прод       => прод
./scripts/ship.sh --prod-only  # main уже в порядке, двинуть только прод
```

Нужен `git`; ssh не нужен вовсе. Отсюда и смысл: работать можно из облачной
сессии и с телефона, а не с одной машины, где лежит ключ. `push-deploy.sh`
зовёт этот же скрипт (`--prod-only --yes`), как зовёт `sync-env.sh` для
env-файла.

**Дорог две, и `gh` не обязателен.** Ветку двигает либо `gh` серверной
операцией, либо обычный `git push` — что найдётся, в этом порядке.

Дорога была одна, через `gh`, и с доводом: «в облачной сессии площадка
запрещает пуш в любую ветку, кроме собственной, а серверные операции GitHub
под запрет не попадают». Довод оказался неверен — по крайней мере не везде:
из облачной сессии пуш в `main` и `production` прошёл обычным `git push`. А
вот `gh` там как раз не оказалось, и скрипт умирал первой строкой проверок —
то есть был мёртв ровно в том месте, ради которого написан.

Поэтому порядок, а не замена: `gh` остаётся первым (он проверен, ему не нужны
объекты в локальном репозитории, и там, где пуш действительно запрещён, он
единственный сработает), но его отсутствие больше не отказ. Неавторизованный
`gh` считается отсутствующим — толку от него ровно столько же. Какой дорогой
пошли, скрипт говорит вслух, но только когда она вторая.

Обе дороги двигают ветку **только перемоткой**: у `gh` это проверка предком
перед `PATCH`, у `git` — сам сервер, потому что пуш без `--force`.

**Только перемотка, и в обе стороны.** В `main` ветка вливается перематыванием
`main` на её вершину, а не merge-коммитом: история здесь линейная и держится на
том, что каждое сообщение коммита — отдельная мысль, а `Merge branch …` их
прячет. Отстала ветка — громкий отказ с советом `git rebase origin/main`, и
чинится это в той же сессии, где ветка лежит. `production` двигается только на
`origin/main` и только вперёд.

Стережёт `scripts/test-ship.sh` — восемнадцать случаев, и большая часть про
**отказ**: грязное дерево, незапушенная ветка, отставшая ветка, запуск с
`main`, `main` ушедший мимо ветки, прод без просьбы. `gh` подменён заглушкой,
сети не надо, секунда в CI.

**Обе дороги проверяются порознь, и это не перестраховка.** Шесть случаев
гоняются с заглушкой, отвечающей отказом на `gh auth status`, — то есть по
второй дороге, — и смотрят они не в журнал заглушки, а в настоящий
bare-репозиторий: раз пуш идёт git'ом, правда о том, куда встала ветка, лежит
только там. Каждый из шести вдобавок проверяет, что скрипт **сказал**, какой
дорогой идёт: иначе «прошло» значило бы лишь «ветка встала куда надо», а какой
из двух дорог — неизвестно. Непроверенная вторая дорога повторила бы ту самую
поломку молча.

#### Право двигать эту ветку — вопрос не технический

Запрет площадки на пуш выглядит защитой, но защищает не то — и с тех пор, как
дорог стало две, это видно ещё отчётливее. `gh` ходит токеном пользователя, и
`gh api … PATCH refs/heads/production` двигает ветку без единого пуша; а там,
где `gh` нет, проходит и сам пуш — проверено, из облачной сессии в `main` и
`production`. То есть выкатить прод из облака **можно** обеими дорогами, и
удерживает от этого не механизм, а правило.

Правило записано в навыке `deploy` и сформулировано как правило про живые
запросы в Anthropic: **разрешение спрашивается про каждый запуск**. «Доделай и
выкати» — разрешение; «делай что нужно» и режим без вопросов — нет. Слияние
чужой ветки в `main` под то же правило: оно увозит работу на стенд и делает её
общей. Через пять минут
прод стоит на новом коде. `push-deploy.sh` с ноутбука по-прежнему работает и
двигает ветку сам, а потом не ждёт опроса, а дёргает `deploy.sh` по ssh —
ради вывода перед глазами.

**Чего этот путь не умеет — возить `.env.prod`.** Файл лежит вне git, главная
копия на ноутбуке, и опрос про него не знает ничего. Меняли набор
переменных — выкатка с телефона доедет со **старым** env-файлом, а
`VITE_GOOGLE_CLIENT_ID` вшивается в бандл на сборке. Порядок тогда такой: с
ноутбука `./scripts/sync-env.sh prod`, и только после этого двигать ветку.
Разъехались копии или нет — `./scripts/check-secrets.sh`.

Три вещи, которые скрипт стережёт, и каждая стоила бы молчаливой поломки:

- **это точно прод?** Белый список, как у скриптов стенда: имя контура должно
  быть ровно `lesson-tracker-prod`, пустой ответ — отказ. Спрашивается двумя
  способами (env-файл, затем префикс имён контейнеров) по той же причине, что
  и в `contour_matches_machine`: у прода строки `COMPOSE_PROJECT_NAME` в
  env-файле нет;
- **на той ли ветке дерево на сервере?** `deploy.sh` тянет `git pull --ff-only`
  **текущую** ветку, а не ту, за которой следит опрос. Останься сервер на
  `main` — сравнение шло бы с `production`, а тянулся бы `main`, то есть прод
  выкатывал бы то, чего у него не просили;
- **ветку не двигали назад?** Откат — это не перемотка вперёд, `git pull
  --ff-only` на него не согласится, и скрипт упал бы внутри `deploy.sh`
  невнятной ошибкой git. Вместо этого он говорит прямо и не трогает
  работающий прод: откат делается человеком.

**Упавшая выкатка повторяется на следующем тике.** Это не подстраховка, а
починка дыры: `deploy.sh` тянет код сам, и падает уже **после** `git pull` —
дерево стоит на `origin/<ветка>`, и следующий тик выходил бы на сравнении
голов как «нечего выкатывать». Снаружи это худший из возможных видов: причину
устранили, а контур молчит до следующего чужого коммита. Отметка
(`~/.prod-autodeploy.failed`, у стенда своя) ставится после неудачной попытки
и снимается после удачной; оба опроса устроены одинаково.

Поймано на замке двери контура: он отказывает, пока в env-файле нет списка
допущенных, — и без отметки стенд не выкатился бы и после того, как список
туда добавили. Дыра при этом была общая: так же вело себя любое падение
сборки.

Стережёт это `scripts/test-prod-autodeploy.sh` — секунда, без контейнера, в
CI рядом со сторожем хука Anthropic. Проверяет он **обе** стороны: и что
выкатывает, когда ветка ушла вперёд, и что отказывается во всех четырёх
случаях выше. Сторож, знающий только про успех, пропустил бы ровно то, ради
чего проверки написаны, — и на первом же прогоне он это доказал, поймав в
самом скрипте молчаливый выход: без `.env.prod` `sed` отдаёт код 2, `pipefail`
пропускает его наружу, а `set -e` убивает скрипт **до** строки, которая
объяснила бы, что случилось. В crontab это выглядело бы как «прод не
обновляется, и в логе пусто». Та же ловушка нашлась в `staging-autodeploy.sh`
и вылечена там же.

`push-deploy.sh` со своей стороны отказывается двигать `production`, если та
ушла мимо `main`, и **не форсит**: на том конце живая школа, и «наверное, я
знаю лучше» здесь стоит откатом чужих данных к чужому коду.

#### Сколько это занимает

Замерено 22 августа 2026 на боевой машине. Числа нужны не из любопытства: от
них зависит, ждать выкатку глядя в терминал или уйти и вернуться.

| что выкатываем | сколько | почему столько |
|---|---|---|
| прозу (`*.md`, правила) | **8 с** | образы не меняются, backend не пересоздаётся вовсе |
| код фронта и сервера, зависимости прежние | **43 с** | пересобирается слой `COPY`, backend пересоздаётся |
| ничего (повторный `deploy.sh`) | ~1 с на сборку | всё из кэша, `up -d` не трогает контейнеры |
| зависимости (`package.json`, `requirements.txt`) | **не замерено** | `npm ci` и `pip install` выпадают из кэша, это минуты |

Куда уходят эти 43 секунды, по журналу контейнеров: сборка образов ~10 с,
ожидание здоровой базы и пересоздание backend'а ~10 с, старт backend'а до
первого ответа gunicorn **6.4 с** (из них `bootstrap` 2 с и `collectstatic`
1.6 с; `migrate` на пустом наборе — 50 мс), остальное — проверка ответа,
уборка старых образов и запрос к сайту снаружи.

Две вещи, которые стоит знать заранее:

- **восемь секунд на прозу — это не «ничего»**, а одноразовый контейнер
  сборки фронта: `up -d` перезапускает его всегда, потому что он уже
  завершился, и `npm ci && npm run build` идёт заново. Сам бандл Vite строит
  за 810 мс, контейнер живёт 4 с;
- **к любому времени добавляется задержка опроса — до пяти минут.** В замере
  ветку передвинули в 11:42:20, cron проснулся в 11:45:03, выкатка кончилась в
  11:45:11. Кому нужен ответ сразу — тому `push-deploy.sh` с ноутбука: он не
  ждёт тика.

#### Один замок на два способа выкатить

Опрос из crontab может совпасть по времени с выкаткой с ноутбука, и два
`docker compose up` над одним стеком — это не гонка данных, а погашенный
сайт. Поэтому оба берут один замок, `~/.prod-deploy.lock`: опрос через
`flock -n` (совпало — просто пропустить этот тик, следующий через пять
минут), `push-deploy.sh` через `flock -w 900` (человек ждёт вывода, и
правильный исход — пойти следом, а не бросить).

Замок один намеренно. Два замка по одному на способ — это тот же случай, что
два переноса `.env.prod`: выглядят одинаково, а защищают от разного, и
однажды расходятся.

### Стенд: второй контур на отдельной машине

Стенд (`staging.lbreslav.com`, отдельный VPS) отличается от прода **только
содержимым env-файла** — ради этого домен, имя контура и пароль и вынесены в
переменные. Что у него своё:

| | стенд | прод |
|---|---|---|
| `COMPOSE_PROJECT_NAME` | `lesson-tracker-staging` | строки нет, работает умолчание |
| `DOMAIN` | `staging.lbreslav.com` | `lbreslav.com` |
| `E2E_TEST_LOGIN` | `true` | строки нет |
| `LOGIN_ALLOWED_EMAILS` | один адрес | пусто — пускаем всех |
| OAuth-клиент Google | свой `client_id` | свой |
| выкатка | сама, из crontab по `origin/main` | из crontab, но по ветке `production` — её двигает человек |
| TLS | Let's Encrypt, свой сертификат | Let's Encrypt |

#### Адреса контуров живут в одном месте

`scripts/contours.sh` — единственный файл в репозитории, знающий, где какая
машина. Его подключают точкой и зовут `contour prod` либо `contour staging`;
дальше готовы `SERVER`, `REMOTE_DIR`, `SITE`, `ENV_SOURCE`, `PROJECT_NAME`.
Пользуются им `push-deploy.sh`, `scripts/sync-env.sh` и
`scripts/check-secrets.sh`.

Заведён он под будущий переезд. Раньше адреса стояли умолчаниями в этих трёх
скриптах — пятью строками, и пока сервер не меняется, это незаметно. В день
переезда это три правки, а забытая четвёртая продолжает молча ходить на
старую машину: ssh проходит, скрипт отрабатывает, ответ 200 — и ничто не
говорит, что сервер не тот.

Поэтому там же `contour_matches_machine`: спрашивает у машины, кем она себя
считает, и сверяет с ожидаемым контуром. `sync-env.sh` зовёт его **до**
перезаписи — затереть env-файл не на том сервере это худшее, что он умеет.

Спрашивает он **двумя** способами, и это не перестраховка:
`COMPOSE_PROJECT_NAME` из env-файла, а если строки нет — префикс имён
запущенных контейнеров. Второй способ появился не из любви к надёжности:
**у прода этой строки в файле нет**, он живёт на умолчании
`${COMPOSE_PROJECT_NAME:-lesson-tracker-prod}` из compose-файла. Сторож,
знающий только про env, на боевой машине молчал бы всегда — то есть ровно
там, где он нужен. Проверено обеими сторонами: прод, указанный на стенд, и
стенд, указанный на прод, оба получают отказ.

Пустой ответ обоих способов отказом не считается: чистая машина перед первым
деплоем выглядит именно так.

#### Клиент Google у контуров разный, и дело не в секрете

Вход идёт **frontend-flow** Google Identity Services: браузер получает
`id_token`, сервер проверяет его подпись по ключам Google. Обмена кода на
токен нет (`did_fetch_access_token=False`), поэтому `GOOGLE_CLIENT_SECRET` в
этом потоке фактически **не работает** — лежит в конфиге allauth и всё.

Работает `client_id`, и работает он аудиторией токена: allauth проверяет
`id_token` с `audience=app.client_id`. Отсюда то, ради чего клиенты и
развели: пока `client_id` был общим, токен, выписанный при входе **на
стенде**, проходил проверку **на проде** — контуры были разделены доменом и
паролем, но не тем, чем удостоверяются.

Новый клиент заводится в той же консоли Google, тип **Web application**, и
из полей нужно ровно одно — **Authorized JavaScript origins** с адресом
контура. Redirect URI не заполняется: редиректа в этом потоке нет.

`VITE_GOOGLE_CLIENT_ID` при смене требует **пересборки фронта** — Vite
вшивает его в бандл. Проверять поэтому надо не env-файл, а сам бандл:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T nginx \
    sh -c "grep -rhoE '[0-9]+-[a-zA-Z0-9_]+\.apps\.googleusercontent\.com' /var/www/frontend | sort -u"
```

Найтись должен ровно один, и совпасть с тем, что в `.env.prod`.

Сертификат стенда выпущен тем же способом, что боевой — `certbot certonly
--webroot` по каталогу `certbot/www`, — и работает это потому, что
`/.well-known/acme-challenge/` выведен из-под пароля явно. Забудь про это,
и выпуск не пройдёт: certbot приходит без учётных данных.

Хук перечитывания конфига ставится **симлинком**, а не копией:

```bash
sudo ln -sf "$PWD/scripts/reload-nginx.sh" \
    /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

Копия разъезжается с репозиторием молча, и узнаёшь об этом при продлении —
то есть через три месяца. Симлинк держит их одним файлом.

Два скрипта обслуживают стенд и **оба отказываются работать, если имя контура
не похоже на стенд**. Проверка написана в белый список: незаданная переменная
означает отказ, а не «наверное, это стенд».

- `scripts/staging-seed.sh` — пересев. `seed_demo` отказывается работать при
  `DEBUG=False`, поэтому посев это короткое окно: включить отладку, посеять,
  выключить. Возврат стоит в `trap` на выходе — окно не переживает ни падения,
  ни Ctrl+C. Цена названа прямо: пока скрипт работает, стенд отдаёт трейсбеки;
  он закрыт паролем, так что это не улица, но и не ноль;
- `scripts/staging-autodeploy.sh` — опрос `origin/main` из crontab. Не вебхук и
  не GitHub Actions: обоим пришлось бы пустить снаружи внутрь (ssh-ключ секретом
  плюс открытый вход, либо слушающий эндпоинт с проверкой подписи). Стенд ходит
  наружу сам, туда же, куда и так ходит за кодом. Выкатывает он тем же
  `deploy.sh` — второго способа выкатывать в проекте быть не должно.
  У прода такой же опрос свой (`scripts/prod-autodeploy.sh`), и отличается он
  ровно одним: следит за веткой `production`, а не за `main`;
- `scripts/staging-seed-watch.sh` — опрос ветки `staging-seed` из crontab.
  Пересев по просьбе, пришедшей извне; сеет он тем же `staging-seed.sh`.
  Отдельный раздел ниже.

#### Пересеять стенд можно и оттуда, где нет ssh

Пересев умел работать ровно на одной машине — на той, где лежит ключ. Это тот
же разрыв, что был у выкатки, и закрыт он тем же приёмом: **просьба едет
веткой, а стенд забирает её сам**.

```bash
./scripts/ship.sh --reseed                  # аргументы возьмёт сам стенд
./scripts/ship.sh --reseed --flush --rich   # или вот эти
```

Ставится опрос в crontab стенда рядом с автовыкаткой — но **на другую минуту**:

```
*/3    * * * * .../scripts/staging-autodeploy.sh    # 0, 3, 6, …
1-59/3 * * * * .../scripts/staging-seed-watch.sh    # 1, 4, 7, …
```

Разнесены они не для красоты. Замок у них общий (см. ниже), и на одинаковом
расписании оба просыпались одной секундой и спорили за него: выигрывал кто
придётся, а проигравший писал в лог «пропуск: выкатка уже идёт» и уходил до
следующего раза. Выкатка от этого приезжала через раз — в логе стенда стояли
десятки таких пропусков подряд, и выглядело это как зависшая выкатка, хотя
зависать было нечему. Минута разницы стоит ноль и убирает спор целиком:
опоздавший приходит, когда первый уже закончил или ещё работает — и тогда
пропуск честный.

**Просьба — это коммит на ветке `staging-seed`**, дерево у него от `main`, а
смысл — в первой строке сообщения: `seed: --flush --rich`. Коммит, а не просто
передвинутая ветка, и на то три причины, каждая из которых иначе всплыла бы
позже:

- «пересей ещё раз» обязано отличаться от «уже сеяли». Ветка, передвинутая на
  ту же вершину `main`, неотличима от вчерашней, и вторая просьба подряд не
  сработала бы вовсе;
- аргументы едут **вместе с просьбой**, а не лежат где-то на сервере;
- `git log origin/staging-seed` на github.com — это и есть история пересевов:
  кто просил, когда и с чем. Отдельного журнала заводить не пришлось.

**Просьба исполняется один раз**, и отметка о ней ставится **до** посева, а не
после. Это выбор, а не небрежность: упавший посев, записанный как
неисполненный, повторялся бы каждые три минуты — то есть сносил бы базу по
кругу, пока кто-нибудь не заметит. Не вышло — в `~/.staging-seed.log` сказано
почему, и просьба посылается заново.

Аргументы приходят строкой из чужого сообщения, поэтому список допустимого
назван явно (`--flush`, `--rich`, `--minimal`, `--root`, `--email=`). Прав это
не даёт никаких — двинуть ветку может только тот, у кого есть доступ на запись
в репозиторий, — но опечатка вроде `--flash` кончается внятным отказом в логе,
а не посевом по умолчанию на живом стенде.

Просьба без аргументов берёт их с самого контура — `STAGING_SEED_ARGS` в
`.env.prod` стенда. Адрес человека, которого надо сделать администратором
школы, это свойство стенда, а не просьбы, и облачная сессия его знать не
обязана.

Замок у пересева **общий с выкаткой** (`~/.staging-autodeploy.lock`), и это
важнее, чем кажется: посев перезапускает backend дважды, а выкатка в это же
время пересобирает стек. Два хозяина у одного стека — не гонка данных, а
погашенный стенд. Один замок значит «стенд занят», кем бы он ни был занят.

Из-за него же опросы и разведены по минутам: на одинаковом расписании они
просыпались одной секундой и спорили за замок, а не работали по очереди.

Стережёт всё это `scripts/test-staging-seed-watch.sh` — двенадцать случаев без
контейнера и без сети, и большинство про отказ. Чего этот путь не умеет — того
же, чего не умеет выкатка веткой: **возить `.env.prod`**. Файл лежит вне git,
главная копия на ноутбуке.

#### Боевую базу на стенд возят руками, и у переноса три грабли

Пересев выдумывает данные, а смотреть иногда надо на **настоящие**: жалоба
приходит про живую школу, и воспроизводится она на её собственных числах.
Готового скрипта для этого нет намеренно — `scripts/backup-db.sh` только
снимает дамп, — поэтому перенос делается руками, и все три грабли вылезают
уже после того, как целевая база снесена.

**Дамп снимается с `--no-owner --no-acl`.** Имена базы и пользователя у
контуров разные: прод и ноутбук — `lessons`/`lessons`, стенд —
`lessons_staging`/`lessons_staging`. Без флагов восстановление упрётся в
несуществующую роль.

**Восстанавливать через снос схемы, а не `--clean`**, и обязательно погасив
backend: он держит соединения, и `DROP SCHEMA` встанет насмерть. Миграции
после заливки идут сами при старте контейнера — но идти им есть куда: прод
стоит на ветке `production` и **отстаёт** от `main`, на котором стенд.

**Хвост дампа — метакоманды psql `\restrict`/`\unrestrict`** (патчи 16.x).
Заливать можно только psql'ом не старше того, чем снимали; на 28 августа
2026 прод 16.14, стенд 16.15 — то есть в эту сторону возить можно, а
обратно надо смотреть.

Порядок — в навыке `deploy`. Два следствия, которые к порядку не сводятся:

- **вложения после переноса битые.** Бакеты R2 у трёх контуров разные
  (`lesson-tracker`, `-staging`, `-dev`), и строки в базе показывают в чужой.
  Это же спасает от главного страха: стенд с боевой базой не выкосит боевые
  вложения через `cleanup_orphaned_files`. Файлы возит отдельно
  `backup_files.py`;
- **на стенде теперь чужие персональные данные** — ученики, учителя, адреса.
  Держит их закрытыми список `LOGIN_ALLOWED_EMAILS` (обе двери, и Google, и
  `/api/test/login/`), а `./scripts/ship.sh --reseed` их сотрёт. Прежде чем
  сеять на стенде, стоит вспомнить, что там лежит.

#### Любой `docker compose` на боевом контуре требует `--env-file`

После перевода конфигов на шаблоны в compose-файлах появился `${DOMAIN}`, и
**любая** команда compose без `--env-file .env.prod` отказывает целиком —
даже `ps` и `exec`, которым домен не нужен вовсе.

Это всплывало дважды, и оба раза отложенно. Сначала хук продления
сертификата — сработал бы вхолостую в ноябре. Потом три скрипта резервного
копирования: они отработали утром, до выкатки, и упали бы следующей ночью,
а узнали бы мы об этом в день, когда копия понадобилась.

Общее у обоих случаев одно: **команда выполняется без человека**. Там, где
человек смотрит на экран, отказ виден сразу; в cron и в хуках — нет.

Поэтому правило простое: **новый вызов `docker compose` с prod-файлом
пишется сразу с флагом**. Проверить, что не забыли, — одной командой:

```bash
grep -rn 'docker compose -f docker-compose.prod' --include='*.sh' --include='*.md' .
```

Она должна не находить ничего.

#### `deploy.sh` обновляет сам себя, и это надо было предусмотреть

Скрипт лежит в том репозитории, который он тянет. После `git pull` на диске
новая версия, а bash продолжает выполнять **старую** — ту, что успел
прочитать.

Стоило это упавшей выкатки прода. Старый `deploy.sh` притянул compose-файлы,
в которых появился `${DOMAIN}`, и позвал compose без `--env-file`, которого
сам ещё не умел: `required variable DOMAIN is missing a value`. Хуже отказа
было состояние после него — **код обновлён, контейнеры прежние**. Сайт при
этом отвечал: nginx держал inode старого `ssl.conf`, которого в дереве уже
не было. То есть прод работал ровно до первого перезапуска контейнера.

Лечится тем, что скрипт сверяет себя с собой после `pull` и, если версия
сменилась, перезапускается ею же (`DEPLOY_REEXEC` не даёт зациклиться).

Правило шире одного скрипта: **всё, что тянет себя из git, обязано после
этого перезапуститься или проверить, что не устарело**. Под это подпадают
`deploy.sh`, `staging-autodeploy.sh` и `prod-autodeploy.sh` (оба зовут
`deploy.sh` — тот перезапустит себя сам) и любой будущий хук, живущий в
репозитории.

#### Дверь контура — список адресов, а не пароль в nginx

Пароля basic-auth в проекте больше нет ни строчки, и убран он не ради
простоты. Он не мог стоять там, где входят.

Basic-auth и токен приложения делят заголовок `Authorization`: `api.js`
ставит `Authorization: Token …` на каждый запрос, явный заголовок вытесняет
basic-auth, и nginx ответил бы 401 на весь API. Поэтому у `location /api/`
стояло `auth_basic off` — то есть **API стенда был открыт всегда**, а
закрыта только страница. Дверь, которую нельзя поставить в проходе, охраняет
не то.

Стоило это ровно того, чем такие двери и кончаются: пароль забыли, а
восстановить его нельзя — в `nginx/auth/htpasswd` лежал хэш, файл в git не
ездил и существовал в одном экземпляре на машине стенда.

Теперь вход закрывает **`LOGIN_ALLOWED_EMAILS`** — список адресов в
env-файле контура, разбор в `backend/accounts/door.py`. Пустой список значит
«пускаем всех, кого пустил Google», и так живёт прод: допуск там даёт
приглашение школы, а список пришлось бы править при каждом новом учителе.

Три вещи, которые в этом решении стоит знать заранее:

- **дверей две, и вторая опаснее первой.** `/api/auth/google/` требует
  настоящего аккаунта Google; `/api/test/login/` за флагом `E2E_TEST_LOGIN`
  выдаёт токен **кому угодно по адресу**. Пока был пароль, снаружи её было не
  достать. Теперь список спрашивают обе, а дев-дверь вдобавок требует токен
  допущенного: подменившийся ученическим токеном ходит в неё **домашним**
  (`devSwitch.homeToken` на клиенте), иначе «войти как» работало бы ровно
  один раз;
- **пара «дев-дверь включена, список пуст» запрещена**, и выкатка на ней
  отказывает — `scripts/check-login-door.sh`, вызов стоит в `deploy.sh` до
  `git pull` и до контейнеров. Причина в том, что код и env-файл приезжают на
  контур **порознь**: код веткой, env-файл через `sync-env.sh` с ноутбука.
  Порядок не гарантирован ничем, и опасный порядок — это открытый стенд.
  Отказ безопасен: контур остаётся на прежнем коде. Сторож замка —
  `scripts/test-check-login-door.sh`, шестнадцать случаев, секунда в CI;
- **`/admin/` закрыт паролем суперпользователя и только им.** Список туда не
  распространяется: там свой вход, паролем, и он никогда не был публичным
  вопросом стенда. С прода это ровно так же и было всегда.

Что появилось взамен убранного: `AUTH_BASIC`, `AUTH_BASIC_FILE`,
`HEALTHCHECK_AUTH`, каталог `nginx/auth/` и строки о нём в `.gitignore`
удалены целиком. Оставшиеся в env-файлах контуров строки безвредны —
их просто никто не читает.

#### Сборка виснет на `apt-get` — смотрите MTU

Ловушка не проектная, а машинная, и стоила часа. На VPS за туннелем у внешнего
интерфейса MTU бывает 1450, а Docker поднимает мосты с 1500. Мелкие пакеты
проходят, крупные теряются молча — `apt-get update` скачивает `InRelease` на
43 КБ и бесконечно повторяет `Packages` на 9 МБ, **не падая**. Выглядит как
медленная сеть, а не как ошибка.

Проверяется одной командой — качаем крупный файл с моста и из сети хоста:

```bash
ip link show docker0 | head -1            # MTU моста
ip -o link show ens3 | grep -o 'mtu [0-9]*'   # MTU хоста
```

Лечится на уровне демона, а не настройками compose: сборку BuildKit ведёт мимо
compose-сети, так что `driver_opts` починил бы только половину.

```bash
echo '{"mtu": 1450}' | sudo tee /etc/docker/daemon.json
sudo systemctl restart docker
docker network prune -f     # старые сети сохранили прежний MTU
```

Измерено на стенде: тот же файл с моста 1500 не скачался за 25 секунд вовсе, с
моста 1450 — 13 МБ за 0.2 секунды.

### Три env-файла и почему они разные

| файл | для чего | `DEBUG` | бакет R2 |
|---|---|---|---|
| `~/projects/lesson-tracker/.env` | разработка: runserver, Vite, `seed_demo` | `True` | dev |
| `~/secrets/lesson-tracker.env.local-prod` | прод-сборка на `http://localhost` | `False` | dev |
| `~/secrets/lesson-tracker.env.prod` | боевой; копия серверного | `False` | **прод** |

Совпадают у них только ключи Google: клиент один на эти три, `http://localhost` есть в
разрешённых origins. `SECRET_KEY`, пароль базы и токены R2 — разные, и это
не гигиена ради гигиены: `seed_demo --flush` чистит бакет целиком, поэтому
один запуск не с тем файлом стоил бы школе всех вложений. Отсюда правило:
**боевой бакет подключается только на сервере**, у локального прод-стека
dev-бакет.

Набор имён переменных у `local-prod` и боевого одинаковый — так видно, что
локальная проверка гоняет ту же конфигурацию, а не её огрызок. Различия
только в значениях: `localhost` в хостах и origins, `NGINX_SSL=false`,
выключенные secure-куки и HSTS (сертификата на localhost нет, а
`SECURE_SSL_REDIRECT` увёл бы проверку в https), пустые `R2_BACKUP_*` —
резерв локально не гоняем, и `backup_files` без них честно откажется
работать.

Прод-стек читает `env_file: .env.prod` и другого имени не знает, поэтому на
время проверки файл кладут в корень проекта копией, а потом убирают:

```bash
cp ~/secrets/lesson-tracker.env.local-prod .env.prod
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
docker compose --env-file .env.prod -f docker-compose.prod.yml down && rm .env.prod
```

`--env-file` тут обязателен: из него compose берёт `DOMAIN` и
`COMPOSE_PROJECT_NAME` для подстановки в сами compose-файлы. Без флага
compose ищет `.env`, не находит `DOMAIN` и честно отказывается —
молча подняться с пустым `server_name` он не может.

Он поднимается рядом с dev — своё имя проекта, свои порты 80/443. В пустой
базе школы нет и войти некуда, поэтому в файле лежит закомментированная
пара `BOOTSTRAP_SUPERUSER_*`: раскомментировать — и будет доступ в
`/admin/`.

HTTPS включается одним флагом `NGINX_SSL=true` в `.env.prod`: `deploy.sh`
добавляет оверлей `docker-compose.ssl.yml`, который подменяет шаблон nginx
на `nginx/ssl.conf.template` и прокидывает `/etc/letsencrypt`. Конфиг с TLS —
отдельный файл, а не закомментированный блок, потому что правка
шаблона руками на сервере сломала бы `git pull` в `deploy.sh`.
Сертификаты выпускает certbot **на хосте** (`certonly --webroot`), продление
делает его systemd-таймер, а `scripts/reload-nginx.sh` в
`/etc/letsencrypt/renewal-hooks/deploy/` перечитывает конфиг в контейнере.

```bash
C="docker compose --env-file .env.prod -f docker-compose.prod.yml"
$C up -d --build
$C logs -f backend
$C down
```

Отличия от dev:

- backend — `gunicorn config.wsgi:application --workers 2`, стадия `prod`
  Dockerfile; код зашит в образ, bind-mount'а нет. При старте выполняются
  `migrate --noinput` и `collectstatic --noinput`.
- `db` не публикует порт наружу — до неё дотягивается только backend.
- `frontend-build` — одноразовый контейнер: `npm ci && npm run build`, кладёт
  бандл в том `frontend_dist` и завершается. nginx ждёт его через
  `condition: service_completed_successfully`.
- nginx раздаёт `frontend_dist` (с fallback на `index.html`) и `static_files`
  по `/static/`, проксирует `/api/` и `/admin/` на `backend:8000`.

Что стоит помнить:

- У prod-стека **своё имя проекта** — `${COMPOSE_PROJECT_NAME:-lesson-tracker-prod}`.
  Без него compose взял бы имя каталога, как у dev, и переиспользовал его
  контейнеры и том с базой. Умолчание оставлено прежним намеренно: env-файл
  без этой переменной обязан дать тот же проект, иначе стек молча получил бы
  новые тома и пустую базу.
- **Внутрь контейнеров** переменные приходят через `env_file: .env.prod`.
  А для `${...}` в самих compose-файлах — имя проекта и `DOMAIN` — тот же
  файл передаётся флагом `--env-file`: по умолчанию compose искал бы `.env`,
  которого в проде нет. Раньше `${...}` не использовался вовсе именно
  поэтому.
  В healthcheck по-прежнему `$$POSTGRES_USER` — его разворачивает шелл
  контейнера, а не compose.
- **Домена в репозитории не осталось.** `nginx/*.conf.template` прогоняются
  через `envsubst` при старте контейнера, `DOMAIN` и `DOMAIN_ALIASES` берутся
  из env-файла. `NGINX_ENVSUBST_FILTER` ограничивает подстановку этими двумя
  именами — без фильтра `envsubst` подставил бы и `$host`, `$uri`,
  `$backend_addr`, то есть переменные самого nginx, и конфиг сломался бы
  молча. `deploy.sh` отказывается работать без `DOMAIN` **до** `git pull`:
  пустой `server_name` уронил бы nginx уже после пересборки.
- `VITE_GOOGLE_CLIENT_ID` нужен **на этапе сборки** фронта: Vite вшивает его
  в бандл. Меняется — нужно пересобрать `frontend-build`.
- **Адрес backend'а nginx держит в переменной** (`set $backend_addr backend:8000;`
  плюс `resolver 127.0.0.11 valid=10s ipv6=off;`), а не в блоке `upstream`.
  Имя в `upstream` резолвится один раз при старте: после пересоздания
  контейнера backend получает новый IP, а nginx продолжает ходить на старый и
  отдаёт 502 до перезапуска. С переменной имя перечитывается по TTL. Обратная
  сторона — `proxy_pass` с переменной не делает подстановку URI, но у нас в
  `proxy_pass` и не было пути, так что запрос уходит без изменений.
- nginx объявлен `default_server`, поэтому отвечает на любой Host (это нужно
  для проверки по `http://localhost`). Django при этом свой `ALLOWED_HOSTS`
  проверяет: запрос к `/api/` с чужим Host получает 400.
- `manage.py check --deploy` на проде показывает **одно** предупреждение —
  `SECURE_HSTS_SECONDS`. Остальные три (`SECURE_SSL_REDIRECT`,
  `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`) читаются из env и включены
  с тех пор, как на сервере появились сертификаты. HSTS оставлен нулём
  сознательно: включается он легко, а выключается только по истечении срока
  у каждого браузера, который его запомнил.
