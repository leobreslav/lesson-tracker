# lesson-tracker

Трекер количества проведённых уроков в учебном году для школьного учителя.
Учитель ведёт учёт по классам/предметам и видит, сколько уроков проведено
относительно плана на год.

Прод: VPS Ubuntu 24.04, домен `lbreslav.com`.
Репозиторий: `git@github.com:leobreslav/lesson-tracker.git`.

## Стек

- **Backend**: Django 5.1, DRF 3.15, Postgres 16 (psycopg 3), gunicorn
- **Аутентификация**: django-allauth 65 + dj-rest-auth 7 + TokenAuthentication
- **Таблицы**: openpyxl — импорт и экспорт учебного плана в xlsx
- **Frontend**: React 19 + Vite 8 (dev-сервер на `http://localhost:5173`),
  react-router-dom 7; перетаскивание в учебном плане — @dnd-kit (core + sortable);
  содержание урока — react-markdown + remark-math + KaTeX
- **Файлы**: Cloudflare R2 через django-storages[s3]; бакет приватный
- **Инфраструктура**: Docker Compose; конфиг через django-environ из `.env` в корне

## Быстрый старт разработки

```bash
docker compose down -v && docker compose up -d
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py seed_demo --email=leobreslav@gmail.com
```

Заполнение базы — это **два разных механизма**, и они намеренно не делят код:

| | `seed_demo` | `bootstrap` |
|---|---|---|
| зачем | посмотреть интерфейс глазами | довести живую базу до рабочей |
| где | только разработка | прод, при каждом старте контейнера |
| данные | выдуманные | ничего не выдумывает |
| удаляет | по флагу `--flush` | никогда |
| при `DEBUG=False` | отказывается работать | работает |

Общий хелпер между ними рано или поздно поправили бы ради одного из них,
поэтому его нет — совпадает только вызов `typical_vacations`/`typical_terms`
из `onboarding`, то есть определение «типового учебного года».

`seed_demo` (`schools/management/commands/`) строит школу так, чтобы в
интерфейсе было видно **разные состояния**: курс с полным планом рядом с
курсом, где план кончается раньше расписания, и с курсом без плана вовсе;
один курс вообще без расписания — под пустые состояния; отменённые уроки с
причинами и пара дополнительных. Ровный однообразный набор прячет ровно те
случаи, на которых ломается вёрстка.

Флаги: `--flush` (снести всё, кроме суперпользователей), `--minimal` (только
школа, год и курсы), `--email=` (привязать свой аккаунт администратором —
иначе в интерфейс не войти, вход только через Google).

Идемпотентность держится на том, что уроки для ручной разметки выбираются
среди **обычных** слотов: дополнительные добавляет сама команда, и если бы
они попадали в нумерацию, второй запуск отменял бы другой урок.

**Файлы и содержание.** Три урока из сорока расписаны — с формулами, целями
MYP и домашним заданием, — у двух есть файлы, у одного внешняя ссылка.
Полка «Алгебра 6, по учебнику» снимается **с настоящего плана курса**, а не
пишется списком: только этот путь переносит содержание и вложения, и только
на нём разделяемость видно руками — импортируйте её в другой курс и
убедитесь, что объект в R2 остался один.

`--flush` чистит и бакет: удаляются `StoredFile` вместе с объектами, и
делается это до `School.objects.delete()` — иначе школа унесла бы строки
каскадом, отложенный на коммит сигнал не нашёл бы их и объекты остались бы
в бакете сиротами. Файлы пропускаются с предупреждением, если `R2_BUCKET_NAME`
и `R2_ENDPOINT_URL` пусты: у стенда браузерных тестов ключей нет, и падать
из-за этого seed_demo не должен — ссылки и содержание всё равно появятся.

`bootstrap` (`accounts/management/commands/`) — список функций-шагов, каждая
идемпотентна и печатает результат. Сейчас шагов два: суперпользователь из
`BOOTSTRAP_SUPERUSER_EMAIL`/`_PASSWORD` (только если суперпользователей нет
вообще; существующий аккаунт с этим адресом повышается, а не дублируется) и
подтверждённый `EmailAddress` для staff-аккаунтов. Нет переменных — шаг
пропускается с предупреждением: контейнер, который не стартует, хуже, чем
недостающая учётка. Новый шаг — это одна функция в `STEPS`.

## Команды разработки

Все команды Django выполняются внутри контейнера:

```bash
docker compose up -d                                  # поднять всё
docker compose exec backend python manage.py <cmd>    # любая команда Django
docker compose exec backend python manage.py test     # весь набор тестов
docker compose exec backend python manage.py cleanup_orphaned_files  # сироты в R2
docker compose build backend                          # после правки requirements.txt
docker compose up -d --force-recreate backend         # подхватить новый образ
docker compose logs -f backend
docker compose down -v                                # снести вместе с данными БД
```

Backend слушает `http://localhost:8000`, frontend — `http://localhost:5173`.
Код примонтирован томами (`./backend:/app`, `./frontend:/app`), runserver и
Vite перезапускаются сами — пересборка нужна только при изменении зависимостей.

`node_modules` лежат в именованном томе, а не в bind-mount: пакеты ставятся
под alpine и не должны смешиваться с хостовыми. Поэтому после правки
`package.json` нужно пересобрать образ **и** пересоздать том:

```bash
docker compose build frontend
docker compose down && docker volume rm lesson-tracker_node_modules
docker compose up -d
```

Тесты клиентской логики — встроенным в node раннером, без зависимостей:

```bash
docker compose exec frontend npm test      # tests/*.test.js
```

Проверяются чистые модули (`calendarLogic.js` и соседние). Сборка Vite
неопределённые переменные не ловит — она соберёт `ReferenceError` молча,
поэтому логику держим под тестами, а страницы прикрыты `ErrorBoundary`.

#### Общие случаи для зеркал

Четыре модуля на клиенте повторяют расчёт сервера, и расходятся они
**молча**: предпросмотр покажет «будет создано 12», сервер создаст 6.
Тесты «про то же самое» с обеих сторон от этого не спасают — они пишутся
порознь и проверяют то, что автор помнил в тот день.

Поэтому случаи лежат в `mirrors/` и читаются обоими прогонами:

| файл | сервер | клиент |
|---|---|---|
| `copy.json` | `schedule/test_mirror.py` | `frontend/tests/scheduleLogic.test.js` |
| `layout.json` | `plans/test_mirror.py` | `frontend/tests/planLayout.test.js` |

Каталог примонтирован в оба контейнера как `/mirrors`, и путь до него из
теста один и тот же — `../../mirrors`, — так что он работает и в контейнере,
и с хоста. `expected` в файле — это поведение **сервера**: он авторитет,
клиент обязан его предсказывать. У каждого случая есть `why`: случай без
объяснения через полгода нельзя ни починить, ни выбросить.

Учебные дни в случаях копирования не перечислены списком, а считаются
каждой стороной своим кодом — заодно сверяется и это зеркало.

**Первый же прогон нашёл три расхождения** в предпросмотре копирования,
все три — в пользу сервера, см. «Копирование».

### Браузерные тесты


Playwright + Chromium в официальном образе, поэтому в WSL ставить нечего.
Стек свой (`docker-compose.e2e.yml`, имя проекта `lesson-tracker-e2e`):
nginx с **собранным** бандлом, gunicorn, база в tmpfs. Против dev-сервера
гонять бессмысленно — вёрстка и `ReferenceError` ломаются именно в сборке.

Два отличия от прода, оба вынужденные: `DEBUG=True` (иначе `seed_demo`
откажется работать, а его защита дороже совпадения флага) и
`E2E_TEST_LOGIN=true`. Ключей R2 у стенда нет намеренно: тесты не должны
писать в чужой бакет, поэтому в этих прогонах у уроков есть содержание и
ссылки, но нет файлов — жизненный цикл файла проверяют питоновские тесты.

`backend` объявлен с healthcheck, и nginx ждёт именно его, а не просто
старта контейнера. Команда backend'а выполняет `migrate`, `seed_demo` и
`collectstatic` **до** gunicorn, поэтому «gunicorn отвечает» и значит
«стенд готов». Без этого первый тест иногда получал 502, а при `retries: 0`
это падение всего прогона на пустом месте.

**Вход.** Через Google headless-браузер не проведёшь, поэтому в
`accounts/e2e.py` есть дверь: `POST /api/test/login/` отдаёт токен по email,
`POST /api/test/reset/` перезаполняет базу. Она закрыта трижды: при
выключенном флаге маршруты **не регистрируются вовсе** (обычный 404), вьюха
проверяет флаг ещё раз, а сброс зовёт `seed_demo`, который не работает при
`DEBUG=False`. `E2EDoorTests` следит, что по умолчанию дверь закрыта.

**Главное в этих тестах — не утверждения, а слушатель консоли.** Любая
ошибка в консоли или необработанное исключение роняют тест, чем бы он ни
занимался: дважды страница уезжала в прод с `ReferenceError`, который
`vite build` не видит, потому что код не выполняет. Список исключений в
`e2e/tests/harness.js` короткий и каждый пункт с причиной — иначе сторож
тихо перестаёт быть сторожем. Проверено поломкой: подставленная переменная
в `TermsPanel` валит обход разделов с текстом `ReferenceError`.

Состояние чистое перед каждым тестом: фикстура `seeded` дёргает сброс. В
разметке есть якоря для тестов — `data-date` в сетке календаря,
`data-day-head`/`data-add`/`data-lesson` в недельной сетке; по тексту числа
в нужный месяц не попасть.

`package-lock.json` обновляется без установки пакетов на хост:

```bash
cd frontend && docker run --rm -v "$PWD:/app" -w /app --user "$(id -u):$(id -g)" \
  node:22-alpine npm install --package-lock-only
```

## Особенности окружения

- Разработка в **WSL2 Ubuntu**.
- **Файлы, созданные контейнером, принадлежат root.** После `startapp`,
  `makemigrations` и подобного нужно:
  ```bash
  sudo chown -R $USER:$USER backend
  ```
  Команда требует пароль, поэтому её запускает пользователь вручную.
- `createsuperuser` интерактивна — тоже запускается пользователем.
- `settings.py` читает `BASE_DIR / ".env"`, то есть `/app/.env`, которого
  нет; переменные реально приходят из `env_file: .env` в compose. Вне
  контейнера `manage.py` без экспорта переменных не заработает.
- **Концы строк в `.env` должны быть `\n`.** Если файл сохранён с одними
  `\r` (такое умеют делать редакторы), compose прочитает его как одну
  переменную `DEBUG` со всем содержимым в значении, а остальные молча
  подставятся из умолчаний `settings.py` — и Django не сойдётся с базой по
  паролю. Диагностика: `wc -l < .env` показывает 0 при непустом файле.
  Лечится `tr '\r' '\n'`. Умолчания db в `docker-compose.yml`
  (`${POSTGRES_USER:-lessons}`) и healthcheck на `$$POSTGRES_USER` добавлены
  как раз для того, чтобы контейнер базы в такой ситуации хотя бы поднимался.

## Школы, роли и права

Приложение многошкольное. Часть объектов принадлежит **школе**, часть —
**учителю**, и это деление проходит через весь код.

| школьное (правит администратор, читают все в школе) | личное (только своё) |
|---|---|
| `schools.School` | `schedule.LessonSlot` (`teacher` + `course`) |
| `calendars.SchoolYear` + `DayException` + `Term` | `plans.PlanNode` (`teacher` + `course`) |
| `schedule.Course` — бывший `SchoolClass` | |
| `schedule.Subject` + `GradeLevel` — справочники | |
| `schedule.CourseAssignment` — кто ведёт курс | |
| `schedule.CourseMethodist` — кто утверждает его план | |

`accounts.User` несёт `school` (FK, `null=True`, `PROTECT`) и
`is_school_admin`. Один пользователь — одна школа. Роли не
взаимоисключающие: администратор — это учитель с правами на общие объекты
школы, никакого переключения режимов нет.

Курс общий: два учителя могут вести один и тот же «9Б Алгебра», и внутри у
каждого своё расписание и свой план. Поэтому `unique_together` у слота —
`(teacher, course, date, lesson_number)`, а выборки уровней плана идут по
паре `(teacher, course)` — `services.PlanOwner`.

### Кто ведёт курс

`schedule.CourseAssignment` — `(course, teacher)`, уникальная пара,
многие-ко-многим в обе стороны: курс могут вести несколько человек
(параллельные группы, замена), у человека курсов несколько.

Раньше такой связи не было **вовсе**. Единственным следом «X ведёт Y» был
`teacher` у строки школьного расписания, отчего администратор не мог выдать
курс, не нарисовав человеку неделю, а учитель без расписания видел пустые
списки везде. Нагрузка и расписание — разные вопросы, и теперь у них разные
таблицы.

Список курсов учителя даёт `Course.objects.for_teacher(user)`:
**назначенные плюс те, где у него уже есть уроки или план**. Вторая половина
нужна ровно потому, что назначение можно снять — прятать чужую работу за
правкой администратора хуже, чем показать список чуть длиннее.

Через это ходят все личные выборки: `/api/courses/` (по умолчанию свои,
`?scope=school` — все, это и показывает раздел «Школа»), главная,
`teacher_courses()` в сериализаторах уроков, плана и библиотеки, импорт
школьного расписания. Забыть одно из мест нельзя: `for_teacher` — одна
функция.

**Снятие назначения ничего не удаляет.** Возможных ответов было три, честный
один. Сносить уроки и план вместе со связью — уничтожать чужой год кнопкой
из административного экрана; отказывать, пока есть данные, — тупик в день,
когда учитель уходит из школы. Поэтому: связь уходит, работа остаётся, а
первый DELETE отклоняется кодом `assignment_in_use` со счётчиками —
`?force=true` подтверждает. То же и с отвязкой учителя от школы
(`member_in_use`): уроки и планы сохраняются, снимаются назначения и роль.
Снятие идёт одной транзакцией: назначения без школы или школа без
назначений — состояние, которое потом не отличить от ручной правки
администратора.

**Школьное расписание требует назначения.** `MasterSlot.clean()` и
сериализатор отказывают кодом `not_assigned`, если названный учитель не
назначен на курс; копирование периода проверяет то же самое отдельно, потому
что `bulk_create` проходит мимо `clean()`. Строка **без** учителя по-прежнему
законна: это «нагрузка ещё не распределена».

### Единый механизм прав

Проверки не разбросаны по queryset'ам, а лежат в `config/access.py`:

- `IsSchoolMember` — есть школа (иначе код `no_school`);
- `IsSchoolAdminForWrite` — читают все, пишут администраторы;
- `IsSchoolAdmin` — роль нужна и на чтение (приглашения);
- `SchoolScopedViewSet` — фильтрует queryset по `school_path`
  (`"school"` или `"year__school"` для разметки календаря);
- `TeacherScopedViewSet` — фильтрует по `teacher_path`.

Вьюха выбирает базовый класс и путь до школы; больше руками никто не
фильтрует — забытый фильтр это ровно та дыра, ради которой модуль и заведён.

**Два разных отказа, намеренно.** Чужая школа — **404**: объекта нет в
queryset, и посторонний не должен узнать, что он существует. Своя школа без
роли — **403** с кодом: объект вот он, просто менять его нельзя.

Роль администратора не даёт власти над чужими уроками: она про общие объекты
школы, а не про работу коллег. Суперпользователь Django работает через
`/admin/`, в обычном интерфейсе он рядовой участник своей школы.

### Как устроены тесты прав

Фабрик (factory_boy) в проекте нет и не нужно: объекты создаются напрямую,
а общие фикстуры лежат в `schools/testing.py` — школа, шестеро действующих
лиц (`user`, `admin`, `colleague`, `stranger`, `alien_admin`, `outsider`,
плюс `make_root()`) и билдеры `make_year/make_course/make_slot/make_node`.
Билдеры держат инварианты, которые проверяет API: год слота берётся из
курса, а не задаётся отдельно, иначе фикстура выражала бы состояние
(`slot_year_mismatch`), недостижимое через приложение. `SubFactory` из
factory_boy как раз такие состояния и порождал бы по умолчанию.

Сама матрица объявляется одним вызовом на модель (`schools/matrix.py`):

```python
self.assertSchoolObjectRules(
    list_url="course-list", detail_url="course-detail",
    obj=self.course, create={...}, patch={...},
)
self.assertPersonalObjectRules(
    list_url="lessonslot-list", detail_url="lessonslot-detail",
    obj=self.slot, patch={"is_cancelled": True},
)
```

Внутри — весь перебор: свой учитель читает и не пишет, свой администратор
пишет, чужая школа не отличает объект от несуществующего, без школы —
`no_school`. Новая модель закрывается пятью строчками, и правило меняется в
одном месте на всех.

**Про «чужая школа — 404» есть уточнение**, которое всплыло, когда матрицу
свели в одно место. 404 приходит тому, у кого есть роль администратора:
его останавливает queryset. Рядовой учитель чужой школы упирается раньше, в
проверку роли, и получает 403 — но это утверждение о нём, а не о нашем
объекте. Поэтому тест проверяет не конкретный код, а **неотличимость**:
ответ на наш id совпадает с ответом на id, которого никогда не было.

`schools/test_wiring.py` — сторож поверх роутеров, а не поверх моделей. Он
обходит `config.urls` и требует, чтобы каждая вьюха под `/api/` либо
наследовалась от `SchoolScopedViewSet`/`TeacherScopedViewSet`, либо имела
право из `config.access`, либо лежала в `EXEMPT` с причиной. Плюс проверяет,
что `school_path` реально ведёт в `School`, а `teacher_path` — в `User`.
Потестовая матрица не поймает эндпоинт, для которого тест забыли написать
вовсе, — а это и есть настоящий риск на следующих этапах.

**У `@action` своя проверка**, потому что базового класса ей мало: список и
`detail` он закрывает, а действие внутри ходит в модели своим кодом —
`get_object_or_404` по своему queryset'у, а то и просто `objects.filter`.
Поэтому в матрицу добавлен необязательный `actions=`, и по каждому
действию проверяется то же правило неотличимости: ответ на **наш** id
совпадает с ответом на id, которого никогда не было, — и кодом, и телом.

Тело сравнивается потому, что именно через него утечка и выглядит: у
отфильтрованного списка оба ответа законно `200`, и разница была бы только
в том, пустой он или нет. Из тела вычитается сам id: отказ DRF повторяет
присланное значение («Invalid pk "10"»), и дословно такие тела сравнивать
нельзя.

Действие описывается либо именем маршрута (id в пути), либо парой
«имя, параметр» (id в query-строке, как `?course=`), либо словарём с
методом и телом. Спрашивают чужие; у личных объектов — ещё и коллега с
администратором своей школы.

Полноту списка стережёт `ActionCoverageTests`: он берёт все `@action` из
роутера и требует, чтобы каждое было либо названо в `test_access.py`, либо
записано в `ACTIONS_WITHOUT_ID` с причиной — там действия, у которых
объекта на входе нет вовсе. Иначе список в матрице был бы ручным, а новое
действие в него никто не обязан добавлять.

Проверено поломкой дважды: снятый фильтр по школе в `requested_course`
валит матрицу на четырнадцати подтестах, а действие, забытое в списке, —
`ActionCoverageTests`.

### Суперпользователь и список школ

`is_superuser` значит что-то ровно в одном месте интерфейса — раздел
«Школы» (`/api/schools/`, `Schools.jsx`): список всех школ, создание,
переименование, удаление и приглашение первого администратора. Иначе завести
школу было бы неоткуда: изнутри школы её не создать, а первому администратору
некому выдать приглашение.

Больше нигде роль суперпользователя не действует: в своей школе он рядовой
участник, чужие уроки ему не видны, курсы без `is_school_admin` он не правит —
это закреплено тестами `SuperuserSchoolTests`.

Школа с участниками не удаляется (`PROTECT` на `User.school`), ответ
`school_in_use` называет, сколько человек мешает. Своё название школа правит
через `/api/school/` (PATCH, `IsSchoolAdminForWrite`) — это единственное её
поле, кроме `created_at`.

Суперпользователь без школы не попадает на экран «вас не пригласили»: иначе
установка с пустой базой запиралась бы снаружи — создать первую школу было бы
некому. Он видит приложение и подсказку про раздел «Школы».

### Приглашения

Администратор вписывает email заранее. При входе через Google
`accounts/signals.py` ищет `Invitation` по адресу, **подтверждённому
провайдером** (`sociallogin.email_addresses`, `verified=True`), а не по
введённому пользователем — иначе чужое приглашение присваивалось бы вписыванием
его адреса. Приглашение помечается `accepted_at` и остаётся в базе как история.

Уже состоящего в школе человек второе приглашение не переносит: у него на
школе висит всё расписание.

Удаление курса — `PROTECT`, а не каскад: администратор не должен сносить
чужой год одной кнопкой. Ответ `course_in_use` называет, сколько уроков и
строк плана мешает и чьи они.

### Удаление года — самое разрушительное действие в приложении

Год стоит выше всего: курсы висят на нём каскадом, а на курсах —
назначения, методисты и всё школьное расписание. Удаление года в школе,
которая ещё не завела личных уроков, уносит **всё это разом**, и раньше
подтверждение обещало только «разметку».

Поэтому две вещи. Первая: `GET years/<id>/usage/` считает, что именно
уйдёт, и окно перечисляет это списком — «1 курс школы · 6 назначений · 334
урока школьного расписания · 4 четверти · 7 дней разметки». Числа берутся с
сервера: только он знает, что накопилось.

Вторая: если внутри курсов есть личные уроки или строки плана, удаления не
будет вовсе — `year_in_use` со счётчиками, как `course_in_use` рядом.
Раньше их сопротивление приезжало пятисоткой: `PROTECT` стоит на
`LessonSlot.course` и `PlanNode.course`, и `ProtectedError` никто не ловил.

Проверка стоит **до** `delete()`, а не в обработчике исключения, ради
текста: `ProtectedError` знает только про `Course.year` — первую связь на
пути, — а сказать надо про уроки и план, из-за которых курс и не удаляется.
Обработчик всё равно оставлен: между проверкой и удалением коллега может
завести первый урок.

## Язык проекта и локализация

**Язык разработки — английский.** Имена, комментарии, докстринги, тексты
ошибок и сообщений бэкенда пишутся по-английски. Русский — один из языков
интерфейса, без привилегий; язык интерфейса по умолчанию — английский.

### Ошибки с кодом

Каждая ошибка валидации несёт машинный код рядом с английским текстом:

```json
{"code": "term_overlap",
 "detail": "Term overlaps with «1 четверть» (2026-09-01 — 2026-10-25).",
 "params": {"name": "1 четверть", "start": "2026-09-01", "end": "2026-10-25"},
 "field": "start_date"}
```

Все коды перечислены в одном месте — `config/errors.py`, класс `Codes`;
`api_error(code, detail, field=..., **params)` поднимает такую ошибку.
Фронтенд ищет код в словаре `errors.*`, а незнакомый показывает как `detail`,
поэтому новая ошибка сервера никогда не выглядит пустым местом.

Поднимается это **не** через `serializers.ValidationError`, а через свой
`ApiError(APIException)`: DRF прогоняет ошибки из `validate()` через
`as_serializer_error`, а тот считает тело словарём «поле → список ошибок» и
заворачивает каждое значение в список — до клиента доехало бы
`{"code": ["term_overlap"]}`. Свой класс летит сразу в обработчик исключений,
заодно сохраняя типы в `params`.

Предупреждения (не отказы) устроены так же: `warning` у слота и строки
`warnings` при импорте CSV — это `{code, detail, params}`, ключи
`warnings.*` в словаре.

Обычные ошибки полей DRF (`{"year": ["Invalid pk"]}`) остались как были: их
показывает `api.js` первым попавшимся текстом, кода у них нет.

### Словари

`react-i18next`, инициализация в `frontend/src/i18n.js`, словари —
`frontend/src/locales/en.json` (первоисточник) и `ru.json`. Ключи
иерархические и по смыслу: `nav.schedule`, `dashboard.demo.title`,
`errors.term_overlap`, `common.save`.

- Множественное число — только через i18next (`common.lessonCount` +
  `_one/_other` в английском, `_one/_few/_many` в русском). Склеивать строки
  руками нельзя.
- Подстановки — только параметрами (`{{name}}`), не конкатенацией.
- Даты и дни недели нигде не зашиты: `frontend/src/dates.js` строит их через
  `Intl.DateTimeFormat` по текущему языку. А вот первый день недели от языка
  **не** зависит: неделя всегда начинается с понедельника
  (`weekStart.js`). Раньше зависела — русский читал с понедельника,
  американский английский с воскресенья, — и это было ошибкой: школьная
  неделя понедельничная независимо от языка интерфейса, а под ней всё и так
  считает от понедельника (нумерация `date.weekday()`, `weekend_days`,
  округление периода копирования до целых недель). Переключение языка
  перекладывало сетку расписания, хотя ни один урок не двигался.

`tests/locales.test.js` держит это в узде: наборы ключей en/ru совпадают,
у русских счётчиков есть все три формы, подстановки в паре языков одинаковы,
`1/2/5/11/21 урок(а/ов)` считаются правильно, каждый ключ, который зовёт код,
есть в `en.json` (иначе опечатка в `t()` молча показала бы сам ключ), ключи,
собираемые из кода на лету (`dayStatus.*`, `calendar.kind.*`, `nav.*`,
`dashboard.steps.*`), есть для всех своих значений, и **у каждого кода из
`config/errors.py` есть фраза** — забытый код доехал бы до пользователя
английским `detail`. Ради последней проверки в dev-compose файл кодов
примонтирован в контейнер фронта (`/backend/config/errors.py:ro`): путь тот
же, что и с хоста.

**Сверка идёт в обе стороны.** «Ключ из кода есть в словаре» ловит опечатку
в `t()`; «ключ из словаря кто-то зовёт» ловит мусор — раздел переделали,
фразы остались, и через полгода живую от памятника прошлой версии экрана не
отличить. Ключей шестьсот, руками это не проверяется. Динамические ключи
считаются живыми по префиксу (`t(\`nav.${section}\`)` держит весь раздел), а
строка-ключ ищется где угодно в файле, а не только сразу после `t(`: ключ
приезжает и тернарником, и списком. Ложно живой ключ здесь дешевле ложно
мёртвого — второй означает удалённую фразу на экране.

Зеркала (`calendarLogic.js`, `scheduleLogic.js`, `planLogic.js`,
`planCsv.js`) слов не содержат вовсе — как и их серверные оригиналы. Наружу
они отдают коды и числа: предупреждения разбора CSV — те же `{code, params}`,
что у сервера, а `describeCopyResult` и `suggestVacations` принимают `t`
или готовые названия. Названия каникул и терминов, созданных кнопкой
«типовые каникулы», — это контент в базе, поэтому пишутся на языке учителя.

### Выбор языка

Поле `User.language` (`en`/`ru`, по умолчанию `en`), читается и пишется через
`/api/me/`. Переключатель — в меню пользователя в верхнем баре: язык меняется
сразу, запрос на сохранение уходит следом и его результата интерфейс не ждёт.
До входа профиля нет, поэтому `Login` берёт язык из `navigator.language` и
падает на английский, если такого у нас нет.

Демо-данные первого входа — это **контент в базе**, а не интерфейс: они
создаются на языке учителя (`onboarding/services.py`, `DEMO_CLASSES`,
`VACATION_TITLES`, `TERM_NAMES`) и при смене языка не переписываются.

## Аутентификация

Пользователь опознаётся по **email**, поля `username` нет:
`accounts.User(AbstractUser)` с `username = None`, `USERNAME_FIELD = "email"`,
`REQUIRED_FIELDS = []` и своим `UserManager`. `AUTH_USER_MODEL = "accounts.User"`.

Схема входа — **frontend-flow**: React получает `id_token` от Google Identity
Services и шлёт его на бэкенд; бэкенд проверяет подпись по ключам Google.
Redirect URI на стороне Django не используются.

Ключи Google берутся из `.env` и подставляются в
`SOCIALACCOUNT_PROVIDERS["google"]["APP"]` — `SocialApp` в админке заводить
не нужно. Фронтенд берёт тот же client_id из `frontend/.env`
(`VITE_GOOGLE_CLIENT_ID`); origin `http://localhost:5173` должен быть в списке
разрешённых в консоли Google Cloud, иначе кнопка GIS не отрисуется.

Включён `SOCIALACCOUNT_EMAIL_AUTHENTICATION`: вход через Google подхватывает
существующий локальный аккаунт с тем же адресом. allauth делает это только
для адресов, которые провайдер отдал подтверждёнными (`email_verified` в
id_token), см. `adapter.authenticate_by_email`.

### Эндпоинты

| Метод | URL | Описание |
|---|---|---|
| POST | `/api/auth/google/` | `{"id_token": ...}` или `{"access_token": ...}` → `{"key": "<токен DRF>"}`; при первом входе пользователь создаётся по email |
| POST | `/api/auth/logout/` | удаляет токен; требует заголовок `Authorization` |
| GET | `/api/me/` | `id`, `email`, `first_name`, `last_name` |
| PATCH | `/api/me/` | правка `first_name` и `last_name`; `email` только на чтение, `PUT` отключён |

Запросы к API авторизуются заголовком `Authorization: Token <ключ>`.
`DEFAULT_PERMISSION_CLASSES = IsAuthenticated` — все новые вьюхи закрыты
по умолчанию.

Вход по паролю в `/admin/` продолжает работать: в
`AUTHENTICATION_BACKENDS` оставлен `ModelBackend` рядом с бэкендом allauth.

### Подводные камни, уже разобранные

- Штатный `SocialLoginSerializer` из dj-rest-auth требует `access_token`
  или `code` и падает на «голом» `id_token`. `GoogleLoginSerializer`
  копирует `id_token` в `access_token`; дальше dj-rest-auth сам передаёт
  адаптеру `response={"id_token": ...}`, а `GoogleOAuth2Adapter` проверяет
  подпись, потому что `did_fetch_access_token` остаётся `False`.
- Битый `id_token` поднимает `OAuth2Error`, который dj-rest-auth не ловит,
  и превращается в 500. `GoogleLoginSerializer` перехватывает его и
  возвращает 400.
- В `UserAdmin` обязателен `ordering = ("email",)` — дефолтный ordering
  ссылается на несуществующий `username` и даёт `admin.E033`.
- В `add_fieldsets` нужно поле `usable_password`: Django 5.1 добавил его в
  `AdminUserCreationForm`, без него админка падает с `FieldError`.
- При email-аутентификации allauth вызывает `wipe_password` и делает пароль
  непригодным, если у локального пользователя **нет подтверждённой записи
  `EmailAddress`**. `createsuperuser` такую запись не создаёт, поэтому первый
  вход через Google обнулил бы пароль от `/admin/`. Заводит её шаг
  `bootstrap` — он идёт при каждом старте контейнера и покрывает staff-аккаунты;
  раньше это делала миграция данных, но миграции пересобирались, и её больше
  нет. Аккаунт, заведённый руками не через `bootstrap`, записи не получает —
  её нужно создать самому.
- Неподтверждённый адрес от провайдера allauth уводит на HTML-форму
  `socialaccount_signup`, которой в SPA нет — получался `NoReverseMatch` и 500.
  `accounts/adapter.py` отсекает такой вход, серилизатор отдаёт 400.
- Прокси Vite настроен **без** `changeOrigin`: с ним Host становится
  `backend:8000` и Django отвечает `DisallowedHost`.

## Учебный год и календарь

Приложение `calendars`. Учитель заводит `SchoolYear` (название, границы,
номера выходных дней недели) и размечает его исключениями `DayException`:
праздник, каникулы, перенос рабочего дня. Годы принадлежат владельцу,
`unique_together (owner, name)`.

**Учебный день** — будний день внутри границ года, не накрытый праздником
или каникулами, плюс дни с `kind=workday`. Нумерация дней недели как в
`date.weekday()`: понедельник — 0.

### Приоритет разметки

У даты **ровно один** статус, сколько бы исключений на неё ни наложилось.
Порядок от сильного к слабому:

| | статус | почему так |
|---|---|---|
| 1 | `workday` → `study` | перенос ставят именно поверх нерабочего дня (отработка субботы, рабочий день внутри каникул), поэтому он сильнее всего; не нужен — удаляется, а не перебивается |
| 2 | `weekend` | выходной по расписанию недели учебным и так не был: праздник или каникулы на нём ничего не отнимают |
| 3 | `holiday` | праздник — точечная пометка, он вырезает день из каникул, а не наоборот |
| 4 | `vacation` | |
| 5 | `study` | всё остальное внутри границ года |

Отсюда инвариант, закреплённый тестами:
`study + holiday + vacation + weekend == число календарных дней периода`,
а день со статусом `holiday` или `vacation` — всегда день, который иначе был
бы учебным. Значит потери уроков = `holiday + vacation`, без повторной
проверки на выходные.

Название исключения сохраняется и на выходном (`Day.title` и `exception_id`
заполнены, статус — `weekend`): пометка пользователя не теряется, в сетке
такой день помечен точкой.

Расчёт живёт в `calendars/services.py` и **не зависит от ORM**: на вход
`Period` (отрезок + вид), на выход `Day` (дата + статус). Ту же логику
дальше использует расчёт слотов расписания, поэтому она не размазана по
сериализаторам. Мост между ORM и модулем — `DayException.as_period()` и
`SchoolYear.build_days()`.

### Эндпоинты (`/api/calendar/`)

| Метод | URL | Описание |
|---|---|---|
| GET/POST | `years/` | свои учебные годы; `owner` берётся из токена, в теле не передаётся |
| GET/PATCH/DELETE | `years/<id>/` | детально, вместе с вложенным списком `exceptions` |
| GET | `years/<id>/days/` | развёрнутый календарь: дата, день недели, статус (`study`/`holiday`/`vacation`/`weekend`), название исключения |
| GET | `years/<id>/stats/` | `total` (учебных дней), `by_weekday`, `by_status`, `by_term` и `calendar_days` |
| GET | `years/<id>/usage/` | что стоит на годе: курсы, назначения, школьное расписание, термы, разметка, плюс уроки и строки плана |
| GET/POST | `exceptions/?year=<id>` | исключения; фильтр по году необязателен |
| GET/POST | `terms/?year=<id>` | четверти и семестры |
| GET/PATCH/DELETE | `terms/<id>/` | |
| GET/PATCH/DELETE | `exceptions/<id>/` | |

Календарь и статистика считаются на лету и в базе не хранятся: `/days/` и
`/stats/` вызывают один и тот же `SchoolYear.build_days()`, поэтому разойтись
между собой не могут (тест сверяет их подсчёты).

**День отдаётся одним payload'ом на все страницы** — `services.day_payload`.
Расчёт был общим всегда, а вот ответ однажды разошёлся: календарь слал
`status`, а сводное расписание — ещё и `is_study` рядом с ним. Школьное
расписание читало `is_study` из календарного ответа, получало `undefined` и
красило неучебными **все** дни года, включая будни: уроки не ставились
вовсе. Дата вне всякого года — тот же payload со статусом `outside`
(`services.outside_day`). Сторожит `calendars/test_one_source.py`: одна
дата, оба эндпоинта, сверяются все поля ответа.

Валидация в сериализаторах: `end_date >= start_date`, исключение целиком
внутри границ года, пересечение с исключением **того же вида** запрещено
(разные виды пересекаться могут — перенос внутри каникул это норма).
Названия не уникальны: двое «Каникул» в разные даты — обычное дело,
конфликтом считается только пересечение дат, и сообщение называет
мешающее исключение вместе с его датами («26 октября — 3 ноября»).
Сужение границ года, отрезающее уже размеченные исключения, тоже
отклоняется. `end_date >= start_date` продублирован `CheckConstraint`'ами.

Подводные камни:

- `unique_together (owner, name)` DRF сам не проверит: `owner` в теле
  запроса нет, поэтому в сериализаторе стоит `HiddenField(CurrentUserDefault)`
  плюс явный `UniqueTogetherValidator`. Без него дубль имени давал бы 500.
- Поле `year` у исключения ограничено годами владельца через `get_fields()`,
  иначе можно было бы дописать исключение в чужой календарь.
- `?year=` фильтруется только если значение числовое: иначе `filter(year_id="abc")`
  падает с 500.
- `weekend_days` — `ArrayField`; проект и так только на Postgres.

### Термы

`Term` — четверть или семестр: `year`, `name`, границы, `position`. Термы
**не обязаны покрывать год целиком**: дни между четвертями не входят ни в
один терм, и это нормальное состояние, а не ошибка. Проверяется другое:
границы внутри года и отсутствие пересечений с соседями — сообщение
называет конфликтующий терм. Поиск терма по дате — `services.find_term`
(чистая), мост к ORM — `SchoolYear.term_for_date()`.

Каждый `Day` несёт `term_id` и `term_name` (пустые вне термов), а `/stats/`
отдаёт `by_term` — учебные и календарные дни по каждому терму плюс запись с
`id: null` для дней вне термов. Сумма по термам равна общему числу учебных
дней, это закреплено тестом.

### Страница «Учебный год»

`Calendar.jsx` (список годов, боковая панель, счётчик), `CalendarGrid.jsx`
(сетка месяцев) и `RangeDialog.jsx` (ввод названия каникул). Клик по учебному
дню делает его праздником, по выходному — рабочим днём (перенос), по
одиночному исключению — снимает его; периоды удаляются в списке справа.
Протягивание мышью по нескольким дням открывает диалог каникул.

В боковой панели, кроме счётчика учебных дней и разбивки по дням недели,
показана разбивка по статусам и общее число дней — по ней инвариант
«каждый день посчитан один раз» виден глазами. Ниже — блок термов
(`TermsPanel.jsx`): список с датами и числом учебных дней, добавление,
правка и удаление; пересечение возвращается человеческим текстом.

Терм красит день полосой сверху ячейки (сам день по-прежнему окрашен по
статусу), дни вне термов приглушены. Цвет берётся по порядку терма в году
(`termColors.js`), а не по id, чтобы первая четверть не меняла цвет после
удаления соседней.

Легенда (`CalendarLegend`) стоит **над обеими колонками**, а не внутри
календаря: те же квадратики статусов используются в сводке справа, а изнутри
левой колонки легенда сдвигала месяцы вниз — колонки начинались на разной
высоте. Строк в ней две, и это тоже намеренно: первая говорит, что за день,
вторая — в какой он терм, а у дня есть и то и другое.

Правки оптимистичные: сетка и счётчик пересчитываются сразу, затем ответ
сервера перечитывается как источник истины, а при ошибке состояние
откатывается к снимку. Ради мгновенного пересчёта логика статусов
продублирована в `frontend/src/calendarLogic.js` — **меняете приоритет
видов или правила выходных, правьте оба файла**.

Мелочи, на которых легко споткнуться:

- Диапазон ловится через `mousedown` + `mouseenter`, а одиночный клик — через
  `onClick`: при отпускании кнопки над другой ячейкой браузер `click` на ней не
  генерирует, поэтому обработчики не конфликтуют.
- Обработчик `mouseup` висит на `window` постоянно и читает выделение из ref:
  если вешать его в эффекте по состоянию, быстрый клик успевает пройти до
  подписки и выделение залипает.
- Даты разбираются в `Date` на полдень: с полуночью перевод часов может
  сдвинуть дату на сутки.
- Все модальные окна проекта — `Modal.jsx`, обёртка над нативным `<dialog>`
  с `showModal()`: он рисуется в top layer и центрируется по области
  просмотра, поэтому выделение в самом низу длинного календаря не уводит
  форму за экран. Escape и затемнение фона браузер берёт на себя. У `.modal`
  нулевой `padding`, иначе клик по рамке окна не отличить от клика по фону
  (`event.target === dialog`).
- Протягивание мышью вынесено в хук `useRangeSelection.js` — им пользуются
  и календарь, и расписание.

## Курсы

Приложение `schedule`. Модель `Course` (бывший `SchoolClass`): `school`,
`year` (FK на `calendars.SchoolYear`), `name`, `created_at`; уникальность
`(school, year, name)`, порядок по `name`.

Курс — это параллель и предмет вместе, «9Б Алгебра». Он принадлежит школе:
двое ведущих одну группу пользуются одной записью, иначе их нагрузку не
сравнить. Привязка к году намеренная: в следующем году 9Б становится 10Б, и
это другой курс со своей нагрузкой. `school` и `year` — `CASCADE` (снос года
уносит курсы), а слоты и строки плана держат курс через `PROTECT`.

| Метод | URL | Описание |
|---|---|---|
| GET/POST | `/api/courses/?year=<id>` | курсы школы; POST — только администратор |
| GET/PATCH/DELETE | `/api/courses/<id>/` | правка и удаление — только администратор |
| GET/PATCH | `/api/school/` | своя школа; переименование — администратор |
| GET/POST | `/api/schools/` | все школы; только суперпользователь |
| PATCH/DELETE | `/api/schools/<id>/` | переименовать, удалить (с участниками — отказ) |
| POST | `/api/schools/<id>/invite/` | первый администратор новой школы |
| GET | `/api/school/overview/` | сводка раздела: люди, курсы, назначения, год, расписание |
| GET | `/api/school/members/` | участники школы вместе с их курсами |
| PATCH | `/api/school/members/<id>/` | выдать или снять роль администратора |
| DELETE | `/api/school/members/<id>/?force=` | отвязать от школы; работа сохраняется |
| GET/POST/DELETE | `/api/school/assignments/?course=&teacher=` | кто ведёт курс |
| GET/POST | `/api/school/grades/` | параллели школы |
| GET/PATCH/DELETE | `/api/school/grades/<id>/` | правка и удаление — администратор |
| POST | `/api/school/grades/preset/` | `{through: 11\|13}` — завести годы 1..N |
| DELETE | `/api/school/grades/unused/` | убрать все параллели без курсов |
| GET/POST/DELETE | `/api/school/invitations/` | приглашения; только администратор |

`school` из тела запроса не принимается — `HiddenField(CurrentSchoolDefault)`;
`year` ограничен годами своей школы через `get_fields()`. Дубль имени отдаёт
`non_field_errors` (`UniqueTogetherValidator`).

### Параллели — справочник, а не число

`schedule.GradeLevel`: `school`, `level`, `name`, уникальность
`(school, level)`, порядок по `level`. У `Course.grade` теперь FK на него
(`PROTECT`).

Два поля, и это разные вещи. **`level` — год обучения от первого класса**, по
нему идут сортировка и сравнение; `name` — как это пишут в школе. В системе
MYP «MYP 4» соответствует девятому году обучения, значит `level=9`,
`name="MYP 4"` — иначе в школе, где рядом живут MYP-обозначения и обычные
классы, сортировка поставила бы «MYP 4» между четвёртым и пятым. Это
записано в `help_text` поля и в подсказке «?» у поля формы, потому что
ошибиться тут легко и один раз.

**Верхней границы у `level` нет.** Одиннадцать лет — местная система, а в
британской и IB-школе их тринадцать; предел был бы догадкой о чужой школе, и
сравнивать его здесь не с чем. Снизу — единица: нулевого года обучения не
бывает.

**Год обучения фиксируется, как только на параллели появились курсы**
(`grade_level_locked`). Переименование свободно — имя это ярлык; сдвиг
уровня переставил бы курсы во всех отсортированных списках, и ни один экран
не сказал бы почему. Пустую параллель двигать можно: это просто опечатка.

**Новая школа не получает ничего.** Одиннадцать угаданных строк были хуже
пустого списка: школе с тринадцатью годами или с MYP-обозначениями
приходилось удалять и переименовывать то, чего она не просила. Вместо этого
пустое состояние объясняет, что такое год обучения, а кнопки «Добавить
1–11» и «Добавить 1–13» заводят набор целиком (`POST grades/preset/`,
добавляет только недостающее — нажать дважды не страшно). Имена пишутся на
языке того, кто нажал (`services.grade_name`): «1 класс» или «Grade 1». Это
**контент в базе**, а не интерфейс — записывается один раз и при смене
языка не переписывается, то же правило, что у типовых каникул и
четвертей. Обратная кнопка —
`DELETE grades/unused/`: убирает все параллели, на которых нет курсов, чтобы
после «1–13» в школе с четырьмя не подтверждать удаление девять раз.

Полка библиотеки хранит **число**, а не ссылку: план за девятый год обучения
остаётся планом за девятый год, как бы школа его ни называла, и фильтру
нужно одно сравнимое число. При снятии шаблона предмет и год берутся у
курса, и присланное в теле их **не перебивает**: шаблон — снимок этого
курса, и «Алгебра 9», уехавшая на полку «Геометрией 7», расходилась бы с
ним молча. Форма подставляла значения курса, но поправить их ничто не
мешало; теперь она их и не показывает — только у курса, заведённого до
справочников, спрашивает недостающее, и тогда присланное идёт в дело.

Страница «Классы» (`Classes.jsx`) стала **только на чтение**: выбор года
чипами, список курсов и счётчики уроков (всего, прошло, осталось, отменено)
по запросу `/api/slots/stats/?course=` на каждый курс — их в году единицы,
отдельный API ради этого заводить незачем. Счётчики личные: в общем курсе
каждый видит свои уроки. Показываются только **свои** курсы: те, на которые
назначили.

### Список курсов: строки, а не карточки

У курса две роли и два списка людей, и развёрнутые формы у семи курсов
давали четырнадцать селектов на экране — страница переставала читаться.
Поэтому «Школа → Курсы» это **список строк в одной рамке**: колонки
фиксированной ширины (стрелка · название · предмет и параллель · учителя ·
удалить), лишнее обрезается многоточием, и семь курсов помещаются в экран
без прокрутки — это меряет браузерный тест.

Свёрнутая строка сразу говорит, чего курсу не хватает: «курс никто не
ведёт» и «методист не назначен» — приглушённо, но заметно. Раскрывается
ровно один курс, заливкой; внутри два блока одинакового устройства — «Ведут
курс» и «Утверждает план», у каждого плашки с крестиком и форма «выбрать
человека + назначить». Раскрытие переживает назначение: назначать людей по
одному, каждый раз раскрывая заново, было бы издевательством.

Строки формы внутри (`.course-role .row`) добавлены в общий список
контейнеров «СТРОКА ФОРМЫ» — иначе селекты в них остались бы нестилизованными
и разной высоты с кнопками.

### Раздел «Школа»: четыре вкладки

Была одна страница: название школы, ссылки, курсы вперемешку с добавлением
предметов, учителя вперемешку с приглашениями. Стало четыре вложенных
маршрута под `/school` (`School.jsx` — только рамка с подменю и `<Outlet>`):

| путь | что там |
|---|---|
| `/school` | `SchoolOverview` — название, сводка в числах, ссылки на календарь и расписание, подсказка «что дальше» |
| `/school/teachers` | `SchoolTeachers` — участники, отдельным блоком приглашённые, роли, отвязка, курсы каждого |
| `/school/courses` | `SchoolCourses` — курсы с предметом и параллелью, кто ведёт |
| `/school/reference` | `SchoolReference` — предметы и параллели |

**Назначение делается с двух сторон** — из карточки учителя и из карточки
курса. Это одна и та же строка `CourseAssignment`, но искать её будут
по-разному, смотря о чём человек думает в этот момент; поэтому обе вкладки
пишут в один эндпоинт и читают один и тот же ответ (`teachers` у курса,
`courses` у участника).

## Расписание

`LessonSlot` — один урок одного учителя в конкретный день: `year`, `teacher`,
`course`, `date`, `lesson_number` (1–10), `is_cancelled`, `is_extra`,
`reason`. Уникальность `(teacher, course, date, lesson_number)`, индексы
`(teacher, date)` и `(course, date)`, порядок по `(date, lesson_number)`.

Слот личный: курс общий, а расписание внутри него у каждого своё.

Отдельной сущности «расписание» нет: расписание класса на год — это все его
слоты внутри границ года. Вида урока тоже нет, только два флага: обычный —
оба False, отменённый — `is_cancelled`, внезапный (замена, кружок) —
`is_extra`; комбинация допустима. «Обычный» урок (`is_regular`) — тот, у
которого оба флага сняты: копируются и чистятся оптом только такие.

| Метод | URL | Описание |
|---|---|---|
| GET/POST | `/api/slots/?course=&start=&end=` | свои уроки |
| GET/PATCH/DELETE | `/api/slots/<id>/` | отмена — это PATCH `is_cancelled` + `reason` |
| POST | `/api/slots/copy/` | `{course_id?, source_start, source_end, target_start, target_end, mode}` → `{created, skipped, deleted, conflicts}`; без `course_id` копируются все свои курсы сразу |
| DELETE | `/api/slots/bulk/?course=&start=&end=&only_regular=` | → `{deleted}` |
| GET | `/api/slots/stats/?course=` | `{total, past, remaining, cancelled, extra, cancelled_by_reason}` |
| GET | `/api/slots/agenda/?start=&end=` | сводно по всем классам: `{lessons: {дата: [...]}, days: {дата: {status, title, is_study}}}` |

Урок в неучебный день не запрещён (бывают отработки и субботники), но ответ
несёт поле `warning` с пояснением; считает его та же
`calendars.services.resolve_day`. Валидируется: дата внутри границ года, год
слота совпадает с годом класса, класс принадлежит владельцу запроса.

### Занятость номера

`unique_together (teacher, course, date, lesson_number)` не мешает поставить
два курса на один номер в один день, а физически учитель не может вести два
урока разом. Поэтому есть вторая проверка: у одного владельца в пределах
года не бывает двух **неотменённых** слотов с одинаковыми
`(date, lesson_number)`. Отменённый урок место освобождает — на него можно
поставить другой класс, а вот вернуть его обратно в занятое окно уже нельзя.

Поиск конфликта живёт в `LessonSlot.find_conflict()`, им пользуются и
`clean()` (админка, `full_clean`), и сериализатор, и копирование. Текст
ошибки собирает `services.occupied_message` — «14 октября 3-й урок занят: 9Б».
При копировании такие слоты пропускаются, а их список возвращается в
`conflicts` рядом с `created`/`skipped`.

### Копирование

Цикл источника округляется вверх до целых недель (`schedule/services.py`).
Кратность семи и есть механизм сопоставления дней недели: сдвиг на целое
число недель день недели не меняет, поэтому понедельники источника всегда
попадают на понедельники цели, а двухнедельный источник чередуется, а не
схлопывается. Целевая дата смотрит в источник по остатку от деления
`(target - source_start) % cycle`.

Учебные дни цели берутся из `SchoolYear.build_days()` — своего расчёта у
расписания нет. Неучебные дни пропускаются и попадают в `skipped`, туда же
идут занятые номера. `mode=replace` сначала сносит в целевом периоде только
обычные слоты: отменённые и дополнительные — ручная правка, её массовая
операция не трогает (то же самое делает `only_regular` при удалении).

Без `course_id` копируется расписание целиком: `copy` перебирает те курсы,
где у этого учителя вообще есть уроки и чей год задевает цель, и зовёт `copy_one_class` для каждого —
внутри одной транзакции, потому что уроки, созданные предыдущим классом,
занимают номера для следующего. Итоги суммируются, `conflicts` склеиваются.

#### Три ошибки предпросмотра, которые нашёл общий файл случаев

Клиентское зеркало (`scheduleLogic.planCopy`) считало то же самое «в
общих чертах», и в трёх местах это значило другое число на экране.
Каждое теперь отдельный случай в `mirrors/copy.json`:

1. **Источник — выбранный период, и ничего больше.** Цикл округляется до
   целых недель, поэтому у трёхдневного источника четыре дня недели
   участвуют в раскладке пустыми. Зеркало брало **все** уроки, какие у него
   были на руках, и урок, стоящий в такой день, попадал в цикл: человек
   выделил три дня, а предпросмотр обещал вдвое больше уроков. Достижимо
   двумя способами — выделением части недели и месячным видом, где цикл
   30 дней округляется до 35 и захватывает начало целевого периода.
2. **Отменённый урок чужого курса место освобождает.** Правило записано в
   «Занятости номера», сервер его соблюдает, а зеркало считало занятым
   любой слот в целевом периоде. Предпросмотр говорил «пропущено», сервер
   создавал урок.
3. **`replace` сносит обычные уроки только выбранных курсов.** Зеркало
   считало, что режим освобождает период целиком, и обещало урок там, где
   сервер отвечал конфликтом с соседним курсом.

Одно ограничение оставлено сознательно: при копировании **нескольких**
курсов разом сервер идёт по ним по очереди, и курс может упереться в урок
соседа, который удалится следующим шагом. Порядок обхода предпросмотр не
моделирует — для одного курса он точен, для набора может разойтись на
пересечениях между копируемыми курсами. Причина не в клиенте: у самого
сервера порядок курсов в этом цикле не задан, и правильного ответа тут нет
до тех пор, пока его не зафиксируют.

### Счётчики

`total` — неотменённые уроки, `past` — из них с датой раньше сегодняшней,
`remaining` — остальные (сегодняшний день считается оставшимся), так что
`total == past + remaining`. `cancelled` — отменённые, `extra` —
дополнительные среди неотменённых.

### Страница «Моё расписание»

Единственный экран работы с расписанием: отдельной страницы одного класса
больше нет — два экрана для одной сущности только путали.

`Agenda.jsx` — сводный вид по всем классам поверх `/api/slots/agenda/`.
Неделя (по умолчанию) или месяц, навигация стрелками, «сегодня» и переход к
произвольной дате. В недельной сетке строки — номера уроков 1–10, столбцы —
дни: пустая ячейка это свободное окно (клик — добавить), занятая открывает
меню отмены/возврата/удаления. Неучебные столбцы приглушены и подписаны
причиной, сегодняшний день подсвечен, отменённые уроки перечёркнуты,
дополнительные другого цвета. В месячном виде клик по числу открывает
соответствующую неделю. Чекбоксы классов временно прячут часть расписания
(на сервер это не влияет — фильтр чисто визуальный), внизу сводка за период.

Все правки оптимистичные с откатом; конфликт занятости приходит человеческим
текстом в поле `lesson_number`, а `api.js` показывает первую ошибку поля как
есть — сырых ответов пользователь не видит.

**Массовые операции.** Клик по заголовку дня выделяет его, Shift+клик тянет
диапазон; появляется панель с числом выбранных дней и кнопками «скопировать
на период» и «очистить период». Без выделения кнопка в верхней строке
копирует весь показанный период целиком. В обоих диалогах классы выбираются
чекбоксами (`ClassPicker`).

API при этом не менялся, поменялось только то, откуда его зовут:

- копирование всех курсов — один запрос без `course_id` (сервер делает это
  одной транзакцией и сам следит за занятостью между классами);
- копирование части классов — по запросу на класс, итоги суммируются на
  клиенте; занятость всё равно проверяет сервер, так что урок, только что
  созданный предыдущему классу, заблокирует номер следующему;
- очистка — всегда по запросу на класс: `/api/slots/bulk/` работает с одним
  классом.

Предпросмотр копирования считает `frontend/src/scheduleLogic.js` —
**зеркало** `schedule/services.py` и `stats`, правьте оба места вместе.
Копируются только выбранные классы, а занятость в предпросмотре смотрится по
всем: чужой урок на этом номере всё равно не даст поставить свой.

Кнопка «Скопировать неделю…» (в месячном виде — месяц) отправляет `copy` без
`course_id`: едет расписание всех своих курсов за показанный период. Диалог общий
со страницей класса (`CopyDialog`), но здесь он через `onTargetChange`
подгружает `agenda` целевого периода — поэтому предпросмотр точный, включая
номера, занятые другими классами. Фильтр показа классов на копирование не
влияет: сервер берёт все уроки периода.

**Темы уроков.** Чекбокс «Темы уроков» рядом с фильтром классов включает
показ названия урока из плана под названием класса — мелко, приглушённо, в
одну строку с обрезкой и полным текстом в подсказке. Если урока плана на
слот не хватило (слотов больше, чем уроков), пишем курсивом «(тема не
назначена)» — молчание здесь путало бы: непонятно, темы нет или показ
выключен. Пока темы не загрузились, не пишем ничего: `topics === null`
означает «ещё не знаем», и подпись не появляется зря. Отменённый урок
перечёркивается вместе с темой.

Данные берутся из `/api/plan/layout/agenda/` — одним запросом на все классы,
иначе на сводном экране пришлось бы спрашивать раскладку по каждому классу.
Запрос уходит **только при включённом чекбоксе** и повторяется после любой
правки расписания: отмена урока сдвигает темы у всех последующих слотов.
Состояние чекбокса живёт в `localStorage` (обычное веб-приложение, ограничений
на хранилище нет), чтение обёрнуто в try — в приватном режиме просто не
запоминается.

Одно окно (дата + номер) держит **несколько** уроков: отменённый место не
занимает, поэтому рядом с ним может стоять урок другого класса, и в ячейке
видно оба — отмена перечёркнута, замена обычная. Пока в окне одни отмены,
внизу ячейки остаётся пунктирная кнопка «+». В выпадающем списке при
добавлении не показываются классы, у которых на этом номере уже что-то есть:
даже отменённый урок занимает пару (класс, номер) в `unique_together`.

## Школьное расписание и импорт

Второй этап многошкольной модели. `MasterSlot` — урок в общешкольном
расписании: `school`, `year`, `course`, `teacher` (**nullable**), `date`,
`lesson_number`. Уникальность `(course, date, lesson_number)` — курс не может
стоять в двух местах одновременно, кем бы его ни вели; индекс
`(school, year, teacher, date)`.

`teacher=null` означает «нагрузка ещё не распределена»: администратор
рисует сетку до того, как решено, кто ведёт. Такая строка не конфликтует ни с
кем и **никому не импортируется**.

Вторая проверка, помимо уникальности: у одного **учителя** не бывает двух
уроков на один `(date, lesson_number)` — физически невозможно.
`MasterSlot.find_conflict()` зовут и `clean()`, и сериализатор.

| Метод | URL | Описание |
|---|---|---|
| GET/POST | `/api/school/master-slots/?year=&teacher=&course=&start=&end=` | расписание школы; запись — администратор |
| POST | `/api/school/master-slots/copy/` | копирование периода |
| DELETE | `/api/school/master-slots/bulk/?start=&end=&course=` | массовое удаление |
| GET | `/api/school/master-slots/summary/?year=` | `{total, unassigned, teachers}` |
| GET | `/api/schedule/import-preview/?year=&start=&end=` | что принесёт импорт, ничего не записывая |
| POST | `/api/schedule/import-from-school/` | `{year, courses?, start, end, mode}` → `{created, skipped, deleted, courses, conflicts}` |

### Импорт — разовое копирование, не синхронизация

`schedule/importing.py`. Учитель копирует **свои** строки (`teacher == я`) в
личные `LessonSlot`; дальше это обычные уроки, никак не связанные с
источником. Правка школьного расписания их не трогает, и наоборот — это
проверяют тесты с обеих сторон (`IndependenceTests`).

`courses=null` — все свои курсы. `merge` добавляет и пропускает занятое,
`replace` сначала сносит личные уроки **по выбранным курсам за период**
(включая отмены и дополнительные — интерфейс об этом предупреждает) и потом
кладёт новые. Всё в одной транзакции: полунеделя хуже, чем ничего.

Предпросмотр и сам импорт считает одна и та же `plan_import`, поэтому
показанное и полученное не могут разойтись. План строится покурсно, и уроки,
запланированные на предыдущем курсе, занимают часы для следующего.

### Что переиспользовано

Раскладка копирования — общая: `services.plan_copy` (какие даты куда) плюс
новая `services.place_copies` (что делать с занятым местом). Второе вынесено
из личного расписания и теперь обслуживает три сценария: копирование личного
расписания, копирование школьного и импорт. Различие «занято тем же курсом»
(молча пропустить) и «занято другим курсом того же учителя» (пропустить и
назвать) живёт в одном месте.

Недельная сетка — `WeekGrid.jsx`, один компонент на оба расписания. Что
внутри ячейки и что делает клик, приходит пропсами: у учителя это тема
урока, у администратора — фамилия ведущего.

## Учебный план

Приложение `plans`, одна модель `PlanNode`: `teacher`, `course`, `parent`
(null — верхний уровень), `position` среди сиблингов, `is_section`, `title`,
`note`. Вида урока (контрольная, резерв) нет — поле `kind` удалено вместе с
колонкой миграцией `0002_remove_plannode_kind`.

Дерево **ровно двухуровневое**: наверху вперемешку папки и уроки, внутри
папки только уроки, папка в папке запрещена. Правила проверяет
`services.structure_problems` — её зовут и `PlanNode.clean` (админка), и
сериализаторы, чтобы сообщение было одно.

**Сквозная нумерация нигде не хранится**: `services.number_lessons` считает
её обходом дерева, папки номеров не получают. Позиции плотные (0, 1, 2, …),
после каждой структурной операции уровень перенумеровывается `reindex`.

Ядро (`build_tree`, `number_lessons`, `counts`, `structure_problems`) работает
над любыми объектами с полями `pk`/`parent_id`/`position`/`is_section`, поэтому
тестируется без базы; `get_tree`/`flatten_lessons`/`reindex`/`place`/`move`
подставляют выборку из ORM. `flatten_lessons` — та последовательность уроков,
которая позже ляжет на слоты расписания.

### Как ходит move

Урок верхнего уровня, упирающийся в папку, **входит в неё** крайним
элементом: сверху — первым, снизу — последним. Урок, дошедший до края папки,
**выходит наружу** и встаёт рядом с ней — до или после, в зависимости от
направления. Так одной кнопкой урок проходит весь план, заходя в папки и
выходя из них; тест `test_walking_up_visits_every_position` проверяет, что
сквозной номер при этом меняется не больше чем на единицу за шаг (шаги
входа-выхода номер не меняют вовсе) и доходит до края.

Ответ `{"moved": false}` — не ошибка, а край дерева.

### Страница «Учебный план»

**Страница и таблица разделены.** `Plan.jsx` — состояние, запросы, диалоги,
импорт, полка и эталон; `PlanTable.jsx` — строки, недели, черты термов,
свободные слоты и перетаскивание. Дело не в размере файла, а в том, что
поводы меняться у них разные: таблицу переделывали трижды, и правка колонки
шла в одной функции рядом с логикой публикации шаблона — соседнее ломалось
раз за разом.

Граница проведена по данным, и три состояния остались наверху не по
недосмотру:

- `editing` и `adding` — формы рисуются в строках, но открывают их и кнопки
  под таблицей, а `openAdd` заодно снимает переименование;
- `collapsed` — при смене курса таблица размонтируется (`data` обнуляется на
  время загрузки), и свёрнутые темы разворачивались бы сами.

Свёрнутость хвоста свободных слотов, наоборот, уехала в таблицу: ею не
пользуется никто больше. Она лежит в `localStorage`, поэтому размонтирование
переживает, — а `remembered`/`remember` из-за этого стали отдельным
модулем `remember.js`: три флажка над таблицей остались на странице,
четвёртый уехал.

**Запросов из таблицы не уходит ни одного.** Всё, что меняет данные,
поднимается колбэками: страница знает про `busy`, ошибки и перечитывание
дерева. Перетаскивание поделено по той же линии — сенсоры, попадание
курсора и подсветка цели в таблице, запрос на перенос наверху. Колбэков
одиннадцать, и они собраны в один проп `actions`: списком они читаются как
то, что таблица умеет попросить у страницы, а не как одиннадцать разных
настроек рядом с данными. Данные и вид остались плоскими — их смотрят по
одному.

**`React.memo` на таблице нет намеренно.** Семь пропсов из двадцати —
колбэки, пересоздаваемые каждым рендером страницы; чтобы memo срабатывала,
их пришлось бы обернуть в `useCallback` вместе с общим `run` — восемь
списков зависимостей, каждый из которых при ошибке даёт замыкание на
старые данные. Замер: лишняя перерисовка страницы с планом на сорок уроков
и полусотней свободных слотов стоит **0.45 мс**, доля самой таблицы —
**0.28 мс** (та же страница с пустым планом — 0.17 мс), и случается она на
редких действиях: открыли диалог, показали сообщение, развернули справку.
Ввод в диалогах, вопреки ожиданию, страницу не перерисовывает вовсе:
`PublishDialog` и `UseLibraryDialog` держат своё состояние у себя. А
частый перерендер — перетаскивание, где `setDrop` срабатывает на каждое
движение курсора, — идёт от собственного состояния таблицы, и memo на него
не влияет.

`Plan.jsx`: выбор класса чипами, счётчик сверху, папки блоками с рамкой и
сворачиванием, уроки с отступом, сквозные номера слева. Названия правятся по
клику (Enter — сохранить, Escape — отменить), у урока в той же форме меняется
заметка. Добавление: «+ урок» и «+ тема» внизу, «+» внутри темы и «вставить
после» у каждой строки; форма добавления в конец уровня остаётся открытой для
быстрого ввода подряд, а «вставить после» закрывается, иначе следующий узел
встал бы перед предыдущим. Удаление темы спрашивает через модалку, вынимать
уроки или сносить вместе.

**В интерфейсе это «тема», в коде и здесь — папка (`is_section`).** Слово
выбрано по CSV и библиотеке: в файле столбец называется «Тема», и держать
рядом два имени одной вещи было бы хуже, чем разойтись с именем поля.

Кнопки внизу разложены по двум карточкам, потому что шесть штук в один ряд
читались как один список равнозначных действий: «Добавить» (урок и тема) и
«Импорт и экспорт» (файл слева, библиотека справа, между ними тонкая черта).
Формат выбирается **только для выгрузки** — переключателем `xlsx | csv`
рядом с кнопкой «Экспорт», по умолчанию xlsx; у загруженного файла формат
называет он сам, расширением, поэтому у «Импорта» выбора нет. Переключатель
ростом с соседние кнопки: разновысокие контролы в ряду ловит сторож, и
правильно делает.
Справка о формате CSV висела подписью под кнопками и была длинной; теперь она
раскрывается кнопкой «?» у заголовка карточки (`PlanCsvHelp.jsx`): образец
файла моноширинным, четыре правила, что в файл не едет и чем различаются три
режима. Свёрнутого текста в разметке нет — это состояние компонента, а не
`display: none`.

Правки содержимого и кнопки перечитывают дерево целиком: оно маленькое, так
номера и порядок гарантированно те же, что на сервере. Оптимистично работает
только перетаскивание — см. ниже.

### Таблица плана: CSV и xlsx

**Формат ровно один**, и это главное правило раздела. Файлов, в которых он
живёт, два — текстовый CSV и книга Excel:

```
id,Тема,Урок,Заметка
412,Тригонометрические формулы,Синус и косинус суммы,
,Тригонометрические формулы,Новый урок,добавлен вручную
414,,Повторение,
```

- четыре столбца, шапка обязательна (сравнивается без регистра и пробелов,
  порядок фиксирован);
- **одна строка — один урок**; отдельной строки-заголовка нет вовсе;
- тема повторяется в каждой строке, новый блок начинается со сменой её
  значения;
- пустая тема — «урок вне темы», однозначно;
- пустой id — «урок новый»; заметка принадлежит уроку.

Стилей было три, и разбор угадывал, какой перед ним. У догадки не бывает
неправильного ответа — она всегда «удаётся», — и стоило это фантомных
заголовков, уроков, молча уехавших на верхний уровень, и сдвига всех
столбцов на файле, где id не признался. Поэтому **вместо угадывания —
отказ**: любая непонятная строка отклоняет файл целиком и называет свой
номер. Коды: `csv_header_invalid`, `csv_bad_columns`, `csv_section_row`
(бывший заголовок — говорим прямо, что формат изменился), `csv_row_empty`,
`csv_row_too_long`, `csv_bad_id`, плюс прежние про id. Молчаливых пропусков
строк нет — `warnings` у импорта не осталось вовсе.

Отказ всегда **целиком**: половина применённого файла хуже неприменённого,
потому что непонятно, какая половина. Ошибки при этом собираются все разом —
предпросмотр показывает список, импорт отклоняет по первой.

Что формат выразить не может, и это осознанный размен: **тему без уроков**
(строки без урока не бывает) и **заметку самой темы**. Экспорт их не пишет,
обратный импорт такую тему удаляет; в предпросмотре это видно числом
удаляемых.

**Два файла, один разбор.** Структуру (шапка, столбцы, id, темы, уроки)
понимает `services.parse_plan_rows` — ей всё равно, откуда взялись ячейки.
Форматы различаются только чтением: у CSV это кодировка, разделитель и
кавычки (`parse_plan_csv`), у xlsx — openpyxl (`plans/xlsx.py`, единственное
место, знающее про эту библиотеку). Правила, коды ошибок и sync у них общие,
и разойтись не могут.

**xlsx предпочтительнее, и потому он по умолчанию.** Все работают в Excel и
Google Sheets, а CSV каждый раз приносит одно и то же: кодировку, разделитель
и кавычки вокруг запятой в названии. В книге этого нет вовсе — там сразу
ячейки. CSV остаётся: он открывается чем угодно и его видно глазами.

Что делает выгрузка xlsx помимо данных: шапка полужирная и закреплена
(`freeze_panes`), ширина столбцов по содержимому с потолком, формат ячеек
текстовый (иначе Excel превратит «10.09» в дату), перенос в столбцах «Тема»
и «Урок», лист защищён, а разблокированы все ячейки, **кроме столбца id** —
пароля нет, задача только в том, чтобы id не стёрли не глядя.

При чтении книги значения приводятся к тексту (`xlsx.cell_text`): Excel
хранит id числом, и `412` приезжает как `412.0`, а название вроде «10.09» —
датой. Считать такую ячейку испорченной нельзя, файл на вид правильный.
Читается **первый** лист, остальные называются в ответе (`sheet`,
`sheets_ignored`). Старый `.xls` — другой формат: отказ `file_not_xlsx` с
просьбой пересохранить, вторую библиотеку ради него не тащим.

Разбор (`parse_plan_csv`) и сборка (`build_plan_csv`) — чистые функции,
запись в базу отдельно (`apply_import`). Устойчивость к тому, чем файл
сохранили:

- кодировка: `utf-8-sig` (покрывает и UTF-8 с BOM, и без), иначе cp1251.
  Порядок важен — cp1251 «читает» любые байты и молча выдал бы кракозябры;
  двоичный файл ловится по нулевым байтам, которые Postgres всё равно не
  примет;
- разделитель: не по числу вхождений (запятые бывают внутри названий), а по
  тому, какой даёт одинаковое число столбцов в первых **записях**. Именно
  записях: `csv.reader` с этим разделителем, а не `splitlines()` — перевод
  строки внутри кавычек это часть заметки, и, порезав текст по `\n`,
  эвристика сравнивала бы обрывки. Кавычки поэтому же считает сам reader:
  файл русского Excel, где разделитель `;`, а запятые внутри значений,
  разбирается верно;
- пробелы обрезаются, пустая строка в конце файла пропускается (её пишет
  Excel), пустые столбцы **справа** прощаются — заполненный пятый уже нет.

Экспорт пишется `csv.writer`'ом, поэтому запятые, кавычки, точки с запятой и
переводы строк в названиях экранируются, а не ломают файл. Круговой прогон
на плане, где спецсимвол в каждом названии, — `test_csv_shapes.py`.

Лимиты: 1 МБ и 2000 строк, обе ошибки — понятным текстом. Разбор идёт **до**
транзакции: непригодный файл не должен успеть снести существующий план в
режиме `replace`; сама запись — в `transaction.atomic`.

**Предпросмотр не отказывается ни от чего** — включая нечитаемый файл: и
`file_unreadable`, и `file_not_xlsx` приезжают строкой в `errors`, а не
кодом 400. Иначе единственным следом отказа была бы ошибка в консоли
браузера: диалог показывает список ошибок, а кодов HTTP не разбирает.

Предпросмотр CSV в диалоге импорта считает `frontend/src/planCsv.js` —
**зеркало** `parse_plan_csv`, включая определение кодировки, разделителя,
кавычек и все коды отказа; правьте оба места вместе. Тесты зеркала
(`frontend/tests/planCsv.test.js`) повторяют файлы из `plans/test_csv.py`
теми же ожиданиями — разойтись предпросмотр и импорт могут только если кто-то
поправит один разбор и забудет другой. Импортирует всё равно сервер, файл
уходит к нему целиком.

**Книгу клиент не разбирает вовсе**: тащить в бандл вторую библиотеку ради
предпросмотра незачем, поэтому «как файл прочитан» для xlsx приезжает с
сервера — из `import-preview-xlsx`, то есть всё равно **до** импорта.

### Режимы и синхронизация по id

`mode` **обязателен**: умолчания у разрушительной операции быть не должно.
Раньше POST без поля означал `replace`, то есть «снести план».

| режим | что делает | столбец id |
|---|---|---|
| `sync` | основной: строка узнаётся по id и **обновляется** | нужен хотя бы один заполненный, иначе `csv_nothing_to_sync` |
| `append` | дописать в конец, ничего не удаляя | **не читается вовсе** — иначе строки с существующими id встали бы дублями рядом с собой |
| `replace` | стереть план и создать заново из файла | не читается |

Синхронизация:

- знакомый id → строка **обновляется**: название, заметка и место в дереве.
  Четыре поля содержания и вложения не трогаются вовсе — ради этого режим и
  сделан;
- пустой id → строка создаётся;
- id, которого в файле нет, а в плане есть → строка удаляется;
- порядок строк в файле становится порядком плана. Массовую перестановку в
  таблице делать быстрее, чем перетаскиванием.

**У темы своего id в файле нет** — её строки не существует. Какой теме плана
соответствует блок файла, решают уроки внутри него (`adopt_section`): у
первого же знакомого id спрашиваем, в какой теме он лежит сейчас. Отсюда два
поведения, оба закреплены тестами:

- тему переименовали **во всех** строках — переименовывается заголовок, а не
  создаётся новый;
- тему переименовали **в части** строк — блок делится надвое: значение
  сменилось, значит начался новый блок, и файл не говорит, что имелась в виду
  та же тема. Скрывать это нечем, поэтому предпросмотр называет число новых
  тем отдельной строкой.

Первый блок забирает тему себе (`claimed`), второй получает новую. Круговой
прогон экспорт → sync даёт **ноль созданных и ноль удалённых**, и второй
прогон подряд — тоже: id не переезжают.

Проверки sync — до единой записи: чужой или несуществующий id
(`csv_id_unknown`, один код на оба — подтверждать существование чужой строки
незачем), дубль id в файле, id темы в строке урока (`csv_id_kind_changed`:
у темы дети, осиротить их молча нельзя).

Считает всё это `plan_sync` — без записи, поэтому тем же расчётом
пользуется предпросмотр; пишет `apply_sync`. Порядок внутри записи важен:
сначала создаются темы (уроку под новой темой нужен её id), потом
обновляются строки и только потом удаляются лишние — урок, ушедший из
удаляемой темы, должен успеть сменить родителя, иначе его унесёт каскадом.
Заметку темы `apply_sync` не трогает: файл её не выражает, значит и стирать
нечем.

### Чем платит импорт

`POST /api/plan/import-preview/` отвечает сразу на два вопроса — «как файл
прочитан» и «что будет потеряно» — до того, как что-то произойдёт:
`{mode, rows, lessons, sections, create, create_sections, create_lessons,
update, delete, delete_lessons, with_content, with_attachments, files_lost,
delete_with_content, errors}`. Ничего не пишет и ни от чего не отказывается:
файл с ошибками разбирается до конца, «синхронизировать не с чем» здесь
такая же строка списка, как остальные ошибки.

Первая половина — строка «Строк: 47 · уроков: 44 · тем: 7 · новых: 3 ·
обновлено: 41 · удалено: 2 (из них с содержанием: 1)». `rows` против
`lessons` и есть число строк, которые не прочитались; `create_sections`
отдельно, потому что новая тема при синхронизации почти всегда означает
разделившийся блок.

Нужно это потому, что удаление строки — единственное место, где работа
пропадает молча: содержание и вложения в CSV не выражаются, и `replace`
уносит их вместе со строками. `files_lost` считает **только** те объекты в
R2, у которых уходит последняя ссылка (`files.services.files_at_risk`):
файл, разделяемый с шаблоном или другим курсом, уцелеет, и пугать им —
значит приучать кликать сквозь предупреждения.

Диалог показывает «Будет удалено уроков: 38, из них 12 с содержанием и 5 с
вложениями. 3 файла исчезнут безвозвратно», разворачивает поимённый список
и **требует галочку**: там, где теряется только название, остаётся прежняя
короткая фраза.

### Как выглядит таблица плана

Оформление пришло из прежней ленты «Раскладки» (её больше нет, см. «Ход
года»), и это правильный источник: экран плана и есть та лента, только
рабочая.

- **строка урока — одна линия**: `nowrap` и обрезка многоточием, полное
  название в подсказке. Перенос на две строки растягивал главу вдвое, и она
  переставала читаться целиком;
- **одна сетка на все строки** — и уроки, и главы, и что появится дальше:
  `--plan-columns` = `44px 86px 24px 26px 1fr auto`, то есть неделя · дата
  и день · маркер · номер · название · кнопки. Пока строки раскладывались
  флексом, выравнивание держалось на договорённости — ячейка отступа тут,
  нулевой `padding` там, — и ломалось каждой второй правкой. Теперь
  разъезжаться нечему: колонки заданы один раз;
- **две зоны, которые не смешиваются**. Левая — всё про календарь: номер
  недели, дата, день. Правая — всё про план: маркер, номер урока, название,
  кнопки. Дат в правой зоне нет ни одной; у главы поэтому осталось только
  число уроков, а диапазон её дат убран — он и так стоит в её строках.
  Выключение дат убирает левые колонки (`--plan-columns-bare`), и правая
  зона встаёт к краю;
- **маркеры на одной вертикали, без исключений**. У главы те же колонки,
  что у урока, и никакого сдвига: строка главы отличается **только**
  типографикой. Треугольник свёртки стоит в колонке номера — у главы номера
  нет, а место есть;
- **вложенность показывает отступ названия**, а не строки: название урока
  внутри темы сдвинуто на `--plan-indent`, название урока вне темы стоит на
  одной вертикали с названием темы. Маркеры и номера при этом не двигаются
  — их выравнивание важнее. Пока отступа не было вовсе, урок вне темы был
  неотличим от вложенного, хотя от этого зависит и структура плана, и
  счётчик темы; вертикальной линии вдоль темы не добавляли — отступа
  хватило, а линия на сорока строках снова была бы шумом. Сторожит это
  `planDates.spec.js`: он меряет, что маркеры и номера дают по одной
  вертикали, названий ровно две и расстояние между ними равно переменной;
- **глава — только шрифт**: прописные, полужирный, лёгкая разрядка и чуть
  больше отступа сверху. Ни заливки, ни полосы, ни рамки — любой декор
  слева сдвигал бы её маркер относительно маркеров уроков, а плашка из
  строки делала бы плашку. Рядом с названием только число уроков. Кнопки,
  как и у урока, появляются при наведении;
- **неделя — подпись и заливка**, не строка: «нед 3» в самой левой колонке
  первой строки недели **с датой** — у главы дат нет, и номер недели
  смотрелся бы там случайным, — а сама группа показана заливкой каждой второй
  недели (`--surface-1`). Ни линий между неделями, ни рамок: на сорока
  строках любой декор множится на десять и рябит. Строкой неделя быть
  перестала по той же причине. Числа уроков и дат в подписи нет — первое
  видно по числу строк, второе стоит в каждой из них; остался номер, ради
  которого группировка и нужна. Ширина колонки — 44 px, под «нед 15».
  Нумерация идёт по
  **учебным** неделям и без дыр: неделя, целиком выпавшая на каникулы,
  номера не занимает, а «третья неделя» учитель скажет скорее, чем
  «тридцать девятая». Считает её сервер — он один знает календарь года.
  Глава попадает внутрь недели, а не разрывает её: она принимает неделю
  следующего под ней урока, но подписи не получает. Неделя, в которой не
  оказалось ни одного урока, не получает ни подписи, ни заливки. Чекбокс «Недели» рядом с «Датами»,
  оба помнятся; без дат скобки уходят вместе с ними — номер недели без
  даты не значит ничего;
- **заголовок терма** («1 четверть · 1 сент. — 25 окт.») и **черта
  «сегодня»** — те же, что в раскладке; прошедшие уроки приглушены. Черта,
  выпавшая на первый урок темы, поднимается **над** её полосой: внутри
  блока она читалась бы как часть темы, а это граница между ними;
- **кнопки строки видны при наведении** (`@media (hover: hover)` плюс
  `:focus-within` для клавиатуры). Четыре кнопки на сорока строках — сто
  шестьдесят значков, из-за которых не виден сам план. На сенсорном экране
  наведения не бывает, и там они остаются на месте: долгое нажатие уже
  занято перетаскиванием;
- **сводка — плашки** (`.cards`, как на раскладке, только мельче): слотов,
  в плане, баланс, последний урок, плюс свободные слоты и непоместившиеся
  уроки — эти две кликабельны и ведут на «Раскладку», где видно, **какие
  именно** дни пусты. Показываются, только когда не нули. Прежней строки
  «Уроков: 44. Тем: 7» нет: эти числа и есть плашки.

Порядок черт постоянный — терм, каникулы, сегодня, — от крупного к мелкому:
так они читаются как вложенные, а не как список пометок. Вес по убыванию:
терм (жирный, линия во всю ширину) > глава (прописные) > неделя (подпись и
заливка), и только «сегодня» выбивается цветом — она и не про иерархию.

**Свободные слоты** — даты, на которые уроков плана не хватило, — показаны
такими же строками, только без ручки и номера: это не элемент плана, а
пустое место в расписании; в колонке названия курсивом «свободный урок», по
клику открывается форма добавления. При позиционном сопоставлении они идут
хвостом после последнего урока, и хвост этот бывает в восемьдесят строк,
поэтому по умолчанию он свёрнут в одну: «59 свободных уроков, 21.12 —
31.05». До пяти показываются сразу — сворачивать три строки значит требовать
нажатия ради трёх строк. Чекбокс «Свободные» рядом с «Датами»; без дат
свободных слотов нет — они и есть даты.

Новый урок всегда занимает **первую** свободную дату, на какую бы из строк
ни нажали: раскладка позиционная, и другого места у него нет.

Плотность: строка урока — 29 px. Сорок уроков это ~1160 px одних строк плюс
полосы тем и заголовки термов, то есть ~1530 px; на экране 1280×1024 видно
пятнадцать строк, и без прокрутки весь план такого размера не помещается ни
при какой вёрстке — только свернув темы (▾) или отказавшись от ручки
перетаскивания ради ещё десяти пикселей.

### Даты прямо в таблице плана

Главный сценарий планирования — «тема должна кончиться до каникул»: чтобы
она уложилась в четверть, надо добавить или убрать пару уроков, **видя**,
как план ложится на календарь. Поэтому у строк плана есть две узкие
приглушённые колонки — дата и день недели, — у заголовка темы диапазон её
дат, а между строками рисуются черты: «1 четверть заканчивается · 25 окт.» и
«Осенние каникулы · 26 окт. — 3 нояб.». Без черт даты бесполезны: нужно
помнить наизусть, когда кончается четверть. Сверху закреплена сводка —
слотов, в плане, баланс (зелёный при запасе, красный при дефиците) и дата
последнего урока. Уроки, которым слотов не хватило, подсвечены и вместо даты
говорят «не помещается».

Заголовок терма рисуется по смене терма у слота, поэтому каждый слот в
ленте несёт свой терм целиком, с датами: второго запроса за ними быть не
должно. По той же причине там же лежит номер учебной недели и её
понедельник (`week`, `week_start`). Считает их сервер: нумерация идёт по
неделям, в которых есть учебные дни (`number_weeks`), а календарь года
знает только он.

**Пересчёт мгновенный, и считает его клиент.** Выбор был между «сшивать у
себя» и «спрашивать `/layout/` после каждой правки с дебаунсом», и решает
его состав раскладки. Она состоит из двух половин: календарь (какие дни
учебные, где границы термов, где каникулы) и сопоставление «i-й урок в i-й
слот». Первая от плана **не зависит** и приезжает с сервера один раз —
`/api/plan/layout/slots/`, лента слотов. Вторая от плана зависит целиком, но
это `zip`, а не правило: дублировать на клиенте нечего. Поэтому сшивка
живёт в `frontend/src/planLayout.js`, и строки съезжают в тот же кадр, в
котором урок перетащили, — без запроса, дебаунса и мигания.

Лента перечитывается только при смене курса. Расписание со страницы плана
не правится, а если его поменяли в другой вкладке, даты обновятся при
следующем заходе — цена, которую эта схема платит, и она невелика.

Переключатель «Даты» в сводке: при наборе плана с нуля даты мешают, при
планировании нужны. Состояние живёт в `localStorage`, по умолчанию включено.
Если расписания у курса нет вовсе, дат нет и переключать нечего: «не
помещается» на каждой строке — шум, а не сообщение.

Колонка дат жёсткой ширины и стоит **первой**: даты, номера и названия
выстраиваются в три ровных столбца независимо от того, есть ли у урока
пометки и заметка. Полноценной `<table>` здесь нет: дерево плана — вложенные
списки с перетаскиванием, и таблицей это не выражается; гарантию «колонка не
пляшет» даёт фиксированный `flex-basis`, а сторожит браузерный тест
(`planDates.spec.js`) — он меряет, что все ячейки дат одной ширины и что
названия начинаются на одной вертикали.

### Перетаскивание

@dnd-kit (`core` + `sortable`), по одному `SortableContext` на уровень:
верхний список и содержимое каждой папки. Тянуть можно **только за ручку**
(`⠿`): строки полны кнопок и полей ввода, а на телефоне перетаскивание за
всю строку убило бы прокрутку. У ручки `touch-action: none`, у тач-сенсора
задержка 200 мс — обычный свайп по списку остаётся прокруткой.

Куда попадёт сброс, решает `planLogic.resolveDropTarget`:

- шапка папки — это место **рядом** с ней на верхнем уровне (так урок
  проходит между папками), содержимое папки — место **внутри** неё;
- у пустой папки есть отдельная зона сброса с подписью, иначе положить в
  неё первый урок было бы нечем;
- папку над содержимым другой папки бросать нельзя — цель не подсвечивается
  и сброс ничего не делает.

Вложенные droppable требуют `pointerWithin` вместо `closestCenter`: у папки
прямоугольник накрывает всех детей, и по центрам ближайшей оказывалась бы не
та зона. Для клавиатуры (курсора нет, `pointerWithin` пуст) остаётся
`closestCenter`.

`position` в `move_to` — индекс в уровне **без** перетаскиваемого узла, ровно
как в `place()` на сервере; клиент вычитает единицу при движении вниз внутри
своего уровня. Дерево перестраивается сразу через `planLogic.applyMove`
(зеркало `services`: убрать, вставить, пересчитать сквозные номера), потом
уходит **один** запрос. Ошибка — откат к снимку и сообщение. Кнопки при этом
не блокируются: пока запрос летит, можно тащить другой узел, а повторный
сброс того же узла игнорируется (`pending`), иначе сервер получил бы два
переноса из одного исходного состояния. Дерево перечитывается, когда
последний перенос отгремел.

Кнопки «вверх/вниз» и `move` никуда не делись: на телефоне и в коротких
списках ими быстрее, и они же — запасной путь, если перетаскивание не
работает.

### Счётчики блоков

Сколько уроков в теме, считает `planLogic.countBlocks` — одна функция на обе
страницы, API для этого не трогали: дерево и раскладка и так приходят
целиком. На вход идут строки в порядке отображения (`planRows` для плана,
записи раскладки для «Раскладки»), на выход — счётчик по каждому блоку и
число уроков **вне блоков**.

Правило принадлежности: у урока берётся его собственный `section_id`, где
`null` означает «вне темы» — в нашей модели урок верхнего уровня лежит вне
блока, даже если стоит сразу после папки. Позиционное правило («относится к
последнему заголовку выше») включается только когда поля нет вовсе — это
случай плоского списка вроде CSV. Первая версия делала наоборот, и тест
поймал: уроки после папки приписывались ей.

На «Раскладке» к счётчику добавляются даты первого и последнего урока
блока, число непоместившихся (`no_slot`) и пометка «переходит в …», если
блок начинается в одном терме, а заканчивается в другом. Для надёжной
группировки в `layout_payload` добавлено поле `section_id` — новых запросов
это не создаёт.

### Справочник

`schedule.Subject` — предмет школы («Алгебра»), `unique_together (school,
name)`. У `Course` есть `subject` и `grade` (оба FK, `PROTECT`, `null=True`,
потому что курсы заведены до справочников), и форма создания требует оба —
по ним ищут в библиотеке. Имя курса осталось: там литера и уточнения («9Б»).
Про параллели см. «[Параллели — справочник, а не число](#параллели--справочник-а-не-число)»:
у шаблона хранится год обучения числом, у курса — ссылка на название.

### Модели

`PlanTemplate`: школа, предмет, параллель, название, описание, автор
(`SET_NULL` — полка переживает уход человека), `is_published`. К учебному
году **не привязан**: план по алгебре за 9 класс в сентябре не устаревает.

`PlanTemplateRow` — плоская строка: `position`, `is_header`, `title`, `note`.
Плоская намеренно: дерево плана ровно двухуровневое, а плоский список с
заголовками выражает его полностью — это та же форма, в которой уже работает
импорт и экспорт CSV. У неё есть известный предел: урок верхнего уровня
**после** заголовка неотличим от урока внутри него, поэтому при снятии
шаблона такие уроки уходят в предыдущий блок. У CSV этот предел был тоже,
пока формат не свели к одному: там теперь тема написана у каждого урока и
пустая ячейка говорит «вне темы» прямо. Строке шаблона сказать это нечем —
у неё нет столбца темы, есть только флаг `is_header`.

### Права

Три правила поверх школьного фильтра: черновик виден только автору,
опубликованный — всей школе, править может только автор. Удалять может автор
или администратор школы — библиотека школьная, мусор кто-то должен убирать.

Черновики убраны из queryset (`visible_templates`), а не спрятаны проверкой:
чужой черновик так же отсутствует, как шаблон другой школы, — и в списке, и
в любом поле, которое принимает id шаблона.

Вьюсет наследуется от `SchoolScopedViewSet` ради школьного фильтра, но
заменяет его права: писать здесь можно по авторству, а не по роли.

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/library/templates/?subject=&grade=&mine=true` | опубликованные школы плюс свои черновики |
| GET/PATCH/DELETE | `/api/library/templates/<id>/` | правка — автор, удаление — автор или админ |
| POST | `/api/library/templates/from-plan/` | снять шаблон с плана курса, черновиком |
| POST | `/api/library/templates/<id>/update-from-plan/` | перезаписать строки текущим планом |
| PUT | `/api/library/templates/<id>/rows/` | заменить строки списком целиком |
| POST | `/api/plan/import-from-template/` | взять шаблон в свой план курса |

### Почему строки правятся списком целиком

Отдельных эндпоинтов на строку нет. Список плоский и короткий, а порядок
хранится только в `position` — при записи целиком он равен индексу, и ни
дыры, ни дубля возникнуть не может. Построчный CRUD потребовал бы второй
копии самого хитрого кода проекта (`place`/`reindex`/`move` из
`plans/services.py`) ради формы, у которой вложенности нет вовсе.

Обратная сторона: инлайнового редактора строк шаблона в интерфейсе нет.
Правят план курса и жмут «Обновить шаблон» — шаблон и есть снимок плана.

Предмет и год при обновлении берутся у курса **заново**, тем же правилом,
что при снятии. Иначе они замерзали бы в момент публикации: администратор
поправил год обучения параллели, автор нажал «Обновить», строки
переписались, а на полке шаблон остался под старым годом — и по фильтру его
уже не найти. У курса, заведённого до справочников, спрашивать нечего, и
тогда у шаблона остаётся то, что назвали при публикации.

### Импорт

`library/services.py`. Обе стороны — план→шаблон и шаблон→план — идут через
плоскую последовательность `ImportedRow`, ту же, что у CSV, и пишет её
`plans.services.apply_import`. Поэтому нумерация и поведение replace/append
у трёх способов заполнить план (CSV, библиотека, руками) не расходятся.

Копия — это копия: после импорта план курса ни на что не ссылается.
`update-from-plan` не трогает тех, кто уже забрал себе. Одно исключение —
**файлы**: они не копируются, а разделяются, см. следующий раздел.

## Содержание урока и вложения

### Четыре поля Markdown

У урока (и у строки шаблона) есть `objectives`, `body`, `formative`,
`homework` — абстрактная модель `plans/content.py`, общая для `PlanNode` и
`PlanTemplateRow`: шаблон — это снимок плана, и держать разное было бы
странно. У папки содержания нет вовсе, это проверяет `content_problems` —
одна функция для моделей, сериализаторов и админки.

**Хранится исходный Markdown, никогда HTML.** Формулы в `$…$` и `$$…$$`.
Из-за этого нет и не будет WYSIWYG-редактора: текст должен пережить экспорт
и перенос в LaTeX, а редактор, владеющий разметкой, тихо лишил бы его этой
возможности. Отрисовка живёт ровно в одном месте — `Markdown.jsx`, по дороге
на экран, а не по дороге в базу.

Подводный камень, стоивший отдельного теста: у DRF `CharField` по умолчанию
`trim_whitespace=True`, и он съедает завершающий перевод строки. Для
Markdown это не мелочь — пустая строка отделяет абзац от следующего блока.
Поэтому во всех сериализаторах содержания стоит `CONTENT_EXTRA_KWARGS`.

Второй — на клиенте. `$$…$$` **в одну строку** remark-math считает строчной
формулой: его блочная конструкция хочет разделители на отдельных строках.
Пишут же в одну — так делают Pandoc, Obsidian и любая привычка из LaTeX.
`markdownMath.js` поправляет это одним правилом: абзац, состоящий целиком из
одной формулы, — выключная формула. Важно, что переписывать нужно `data`
узла, а не только `type`: rehype-katex смотрит на класс `math-display`,
который туда кладёт remark-math.

Дерево плана содержание **не возит**: в `/api/plan/` едут только
`has_content` и число вложений, а текст берётся отдельным запросом на урок.
План на двести уроков иначе стал бы мегабайтом JSON ради двух значков.

### Файл и ссылка на него — две модели

`StoredFile` — объект в бакете (школа, ключ, размер, sha256).
`Attachment` — ссылка на него **из конкретного урока** или строки шаблона
(ровно одно из двух), либо внешний адрес (`kind="link"`).

Разделение существует ради одного свойства: при импорте шаблона копии файлов
**не создаются**. Новые `Attachment` смотрят на тот же `StoredFile`, то есть
на тот же объект в R2. Одна модель, где байты и урок вместе, этого выразить
не может.

| | правило |
|---|---|
| дедупликация | тот же sha256 и размер в той же школе — переиспользуем `StoredFile` |
| удаление ссылки | объект уходит, только когда не осталось ни одной другой |
| `on_delete` | `Attachment.stored_file` — `PROTECT`; удаляют с другого конца, от последней ссылки |
| каскады | урок, шаблон, пользователь уносят свои ссылки; чужие и файл целы |

Снос объекта отложен до `transaction.on_commit` (`files/signals.py`).
Внутри транзакции он был бы опаснее: откат вернул бы строки, а байты уже
исчезли — вложение, которое навсегда отвечает 404. При откате же остаётся
`StoredFile` без ссылок, а это задача для `cleanup_orphaned_files`. По той
же причине отказ R2 **сохраняет** строку: строка без ссылок — это заметка
«доделать», а удалённая строка при живом объекте — мусор, который уже никак
не назвать.

В тестах из-за этого каждое ожидание «объект исчез» обёрнуто в
`captureOnCommitCallbacks`. Забыть обёртку — значит получить падающий тест,
а не проходящий по случайности.

### Доступ

Право проверяется на **вложение**, а не на файл: один `StoredFile` может
служить и шаблону на полке, и десятку личных планов, так что у вопроса «можно
ли вам этот файл» просто нет одного ответа.

- чужая школа — **404**, вложения нет в queryset;
- своя школа, чужой урок — **403** с кодом `attachment_forbidden`.

Второе — сознательное отступление от общего правила проекта («личное чужое —
404»): внутри школы все и так знают, что коллеги существуют, и «не ваше»
полезнее, чем притворяться, что id свободен. Опубликованный шаблон читают
все в школе, править вложения может только автор — администратор снимает с
полки шаблон целиком, но не редактирует чужой урок построчно.

### Хранилище

`files/storage.py` — единственное место, знающее про boto3. Ключ:
`files/<school_id>/<uuid>/<имя>`; кириллица транслитерируется (иначе каждый
ключ звался бы `file.txt` и бакет нельзя было бы читать глазами), настоящее
имя едет в `Content-Disposition`.

Особенности R2, ломающие наивную настройку, — в `settings.py`:
`endpoint_url` обязателен, `region_name="auto"`, **никаких ACL** (любой
`default_acl` даёт ошибку), `addressing_style="virtual"`,
`signature_version="s3v4"`. Всё это лежит внутри `client_config`: если
передать его отдельно, django-storages перестаёт читать два последних
параметра из настроек. Там же таймауты — без них недоступный R2 подвесил бы
воркер gunicorn вместо того, чтобы вернуть ошибку.

Файл **не проксируется** через Django: `/api/attachments/<id>/download/`
подписывает ссылку на пять минут и отвечает редиректом. Воркеров два, и
держать один из них на время скачивания нельзя. У той же вьюхи есть
`?json=1`, и им пользуется SPA: запрос нужно авторизовать заголовком, а
заголовок не переживает редирект на чужой origin, — поэтому интерфейс берёт
адрес и переходит по нему сам.

Лимиты: 20 МБ на файл (`FILE_MAX_BYTES`), 5 ГБ на школу
(`SCHOOL_FILE_QUOTA_BYTES`, считается по сумме **уникальных** `StoredFile`),
белый список расширений плюс content-type. Браузер, не узнавший тип, шлёт
`application/octet-stream` — такой файл проходит, если расширение в списке:
отказывать из-за незнания браузера значило бы отбраковывать нормальные
файлы, а настоящую защиту даёт расширение вместе с тем, что файл всегда
отдаётся с `Content-Disposition: attachment` и с чужого домена. `nginx`
пропускает 25 МБ (`client_max_body_size`), запас на оболочку multipart.

Недоступность R2 не роняет страницы: план, панель и список вложений её не
трогают, а загрузка и скачивание отвечают **503** с кодом
`storage_unavailable`.

### Резервный бакет

**Object versioning в R2 не существует** — это функция AWS S3, и её нет ни в
дашборде, ни в API. Поэтому копия делается вторым бакетом:
`manage.py backup_files` раз в сутки переносит в него новые объекты, а
`scripts/backup-files.sh` — обёртка для cron. Ключи отдельные
(`R2_BACKUP_*`): у токена приложения прав на резерв нет вовсе, а у токена
резерва есть доступ к обоим бакетам — благодаря этому копирование серверное,
байты не проходят через VPS.

Три правила делают это резервом, а не зеркалом: команда **никогда не
удаляет** (объект, удалённый в основном бакете, в резервном остаётся — от
этого он и защищает), копирует только новое и изменённое (по размеру и
etag; ключ содержит uuid, так что на практике срабатывает только «нет в
резерве») и идемпотентна. Восстановление — тот же обход в обратную сторону,
`--restore`; `--dry-run` показывает, ничего не трогая.

Соединение с боевым бакетом здесь не проверяется тестами — вместо moto стоит
фейковый клиент (`FakeR2`), потому что проверять нужно решение «копировать
или нет», а не boto3.

**Туда же уезжает дамп базы.** Копия на диске сервера — не копия: диск и
база живут на одной машине и умрут вместе. `scripts/backup-db.sh` снимает
дамп, проверяет, что он не пустой, и отдаёт его контейнеру на stdin —
`manage.py backup_db --name=... --keep-days=7` кладёт его в резервный бакет.
Разделение вынужденное и потому явное: `pg_dump` живёт в контейнере базы,
boto3 — в backend'е, общего тома с хостом у них нет.

Три отличия от копирования вложений, каждое намеренное:

- **свой префикс `db/`.** `backup_files` ходит по `files/`, и с общим
  префиксом `--restore` попытался бы вернуть дампы в бакет вложений;
- **дампы удаляются по сроку**, в отличие от вложений, которые не удаляются
  никогда: копия базы двухмесячной давности — это уже не резерв. Возраст
  берётся из имени файла, а не из `LastModified`: имя означает «за какой
  день дамп», а время объекта — «когда его сюда положили», и при переливке
  бакета оно обнулилось бы. Объект, имя которого не разобралось, не
  трогается вовсе;
- **неудача заливки не отменяет дамп.** Локальный файл уже снят и проверен,
  он и остаётся главной копией; в лог уходит ошибка. Нет `R2_BACKUP_*` —
  предупреждение и пропуск шага: на локальном прод-стенде резерва нет.

### Тесты и хранилище

Ни один тест не ходит в R2, и это обеспечено раз и навсегда —
`config/testing.py`, свой `TEST_RUNNER`, подменяющий `STORAGES["files"]` на
память для всего прогона. Подмена по классам этого не давала: `seed_demo`
загружает файлы, `test_seed_demo` его запускает, и ни тот ни другой не
считают себя тестами про файлы — тридцать объектов доехали до dev-бакета,
прежде чем кто-то посмотрел. `StorageIsNeverRealTests` сторожит настройку.

### Панель урока

Таблица плана остаётся таблицей — тело урока похоронило бы её, — поэтому
содержание открывается по клику по названию урока в панели во всю высоту
экрана (`LessonPanel.jsx`, тот же `<dialog>`, что и остальные окна: top
layer, Escape и затемнение от браузера). Папку по клику по-прежнему
переименовывают на месте: у папки нет содержания, она и есть название.

Две вещи правятся по разным часам, намеренно:

- **текст** — черновик до кнопки «Сохранить»; отсюда пометка о
  несохранённом и вопрос при закрытии;
- **вложение** — отдельная строка на сервере, поэтому применяется сразу.
  Файл, ждущий кнопки, — это загрузка, которая тихо не случилась.

Незаполненные поля свёрнуты; у совсем пустого урока раскрыто одно — то, в
котором начинают писать. Переключатель «Правка / Просмотр» на всю панель, а
не две колонки: на телефоне колонки всё равно схлопнулись бы.

Панель загружается лениво (`React.lazy`): KaTeX с рендерером — 435 КБ, и
учитель, который только переставляет уроки, платить за них не должен.

## Раскладка и «Состояние курсов»

Учебный план — упорядоченный список уроков, расписание — упорядоченный
список неотменённых слотов. Раскладка сопоставляет их **позиционно**: i-й
урок плана в i-й слот. Считает `services.build_layout(lessons, slots)` —
чистая функция, запросы делает вызывающий код.

Числа раскладки — «слотов, уроков, резерв, не помещается, последний
урок» — считает **одна** функция: `services.count_layout` отдаёт `Numbers`,
а `layout_summary` и `course_progress` переводят их на свои словари.
Раньше это были два независимых расчёта под разными именами (`balance` и
`reserve`, `past_lessons` и `done`): числа совпадали, но держались на том,
что обе копии правили вместе. Имена в ответах оставлены прежними — их
читают страницы и словарь, и переименование стоило бы правок в трёх местах
ради нуля.

На клиенте расчёт остаётся — без него не было бы мгновенного пересчёта, —
но и он теперь один: `layoutTotals` и `freeSlots` считают не по ленте
заново, а по **сшитым** строкам, то есть по тому же проходу, который
рисует таблицу. Пока проходов было два, у них было два ответа на вопрос
«поместился ли план»: таблица могла показать дату у последнего урока, а
сводка рядом — «не помещается».

Стерегут это общие случаи `mirrors/layout.json`: девять конфигураций (план
короче, длиннее, ровно, с отменами, с дополнительными, пустой план, пустое
расписание) против обеих серверных обёрток, ленты и клиента. Сверх того
`test_the_entries_and_the_summary_count_the_same_thing` считает те же числа
по самим записям раскладки: если сводка разойдётся с тем, из чего она
собрана, это увидят сразу.

Раскладка **нигде не хранится** и не имеет своих полей в моделях: она
пересчитывается на каждый запрос и потому всегда согласована с планом и
расписанием. Прошлое и будущее в расчёте не различаются: вставка урока в
сентябрьскую тему в ноябре честно двигает всю ленту, включая прошедшие даты
— это ожидаемое поведение, а не баг. `today` участвует только в счётчиках
«прошло/осталось» и в оформлении.

Несовпадение длин ничего не создаёт и не удаляет, только помечает:

- уроков больше, чем слотов → лишние получают `status="no_slot"` и уходят в
  хвост списка («не помещаются в год»);
- слотов больше → лишние получают `status="no_plan"` и остаются на своих
  местах как свободные;
- пустой план или пустое расписание просто дают одну из этих категорий.

`section_title` — папка, в которой лежит урок; у уроков верхнего уровня она
`null` (в этой модели «урок вне темы» — это и есть урок вне папки).

`last_lesson_date` в сводке — дата слота, на который пришёлся последний урок
плана; `null`, когда план не помещается целиком. `balance` — это
`slots_total - lessons_total`: положительный означает запас слотов.

Период в `/layout/` режет **уже посчитанную** раскладку: сопоставление
всегда идёт по всему плану и всему расписанию, иначе номера поехали бы.
Записи без слота (`no_slot`) в срез по датам не попадают — у них нет даты.

Каждая запись раскладки несёт `term_id`/`term_name` — терм берётся по дате
слота. В сводке есть массив `terms`: по каждому терму `slots`, `lessons` и
`balance = slots - lessons`, плюс запись «вне термов» с `id: null`. Суммы по
термам сходятся с общими числами.

**Что означает баланс терма.** Раскладка позиционная, и план не размечен по
четвертям, поэтому внутри целиком заполненного терма баланс всегда ноль.
Минус появляется у записи «вне термов»: туда попадают уроки плана, которым
слотов не хватило вовсе. Плюс — там, где слоты остались свободными. Чтобы
увидеть «в первой четверти дефицит три урока», плану нужна собственная
разметка по термам — этого в модели пока нет.

### Страница «Состояние курсов» — состояние, а не лента

Называлась «Раскладка», и название пережило свой экран: раскладка — это
расчёт, а страница отвечает на вопрос «как идут курсы». Маршрут `/status`,
раздел «Состояние курсов» (en «Course Status»); словарь у него `status.*`,
а данные по-прежнему приходят из `/api/plan/progress/` — эндпоинт про
продвижение по плану, и это разные вещи.

Ленты уроков на ней нет: даты, темы, черта «сегодня» и свободные слоты
уехали в учебный план, где их правят. Оставлять их здесь значило держать
обеднённую копию плана — то же самое, только без редактирования.

`Layout.jsx` показывает **все курсы сразу**: план всегда про один курс, этот
экран про все — учитель ведёт пять и хочет одним взглядом понять, где
проблема. Свёрнутая строка на курс: название · где я · резерв · плашка
состояния. Разворачивается тот курс, где **есть проблема**; если проблем
нет, свёрнуты все — смотреть не на что.

В развёрнутой карточке четыре плашки одного вида — одинаковые отступ, заливка
(`--surface-1`) и высота: **прогресс**, **резерв**, **изменение числа
уроков** и **расхождение с эталоном**.

Прогресс стоит первым: ради него на экран и заходят. Крупно «14 из 44»,
мелко «осталось 30» — врозь эти числа читались бы как три разных
показателя. Считается по **плану**: проведено — уроки, попавшие на
прошедшие даты; осталось — все остальные, независимо от того, хватает ли им
слотов; сумма сходится всегда.

Полоски прогресса нет. Доля пройденного пути на этом экране ничего не
решает: смотрят сюда, чтобы понять, хватает ли дней, а на это отвечает
резерв. Полоска же занимала треть плашки, чтобы повторить крупные числа над
собой картинкой.

**«Изменение числа уроков»** — это `добавлено − отменено`, крупно со знаком,
а под ним слагаемые: «отменено 2 · добавлено 3». Плашка называлась
«потери» и показывала одни отмены с разбивкой по причинам. Разбивка ушла:
это единственное место экрана, где число строк зависело от данных, — плашка
то в две строки, то в пять, и ряд разъезжался; причины видны в расписании,
где отмену и ставили. Из ответа `/api/plan/progress/` разбивка тоже убрана:
поле, которое никто не читает, следующий разработчик прочтёт как обещание.
У `/api/slots/stats/` она осталась — там это счётчики самого расписания. А одни отмены без дополнительных уроков — половина
ответа: у учителя, который отменил два урока и поставил три, расписание не
сократилось, а выросло. **С резервом не путать**: резерв — про план
(`слоты − уроки`), эта плашка — про то, как разошлось само расписание.

**«Расхождение с эталоном»** — два числа подряд, а не сальдо: «+3 добавлено
в план», «2 удалено из плана», подпись «к эталону от 13 авг.» (дата
утверждения, не отправки). Сальдо здесь врало бы: добавленный урок съедает
резерв, удалённый означает выкинутый материал, и «плюс три минус три» — это
не ноль, а шесть правок. Эталона нет — «эталон не утверждён» и ссылка
«отправить на утверждение», ведущая в план: кнопка отправки живёт там.

**Плашки с датой окончания плана нет.** Она повторяла резерв другими
словами — при положительном резерве план кончается раньше конца года, при
отрицательном не помещается вовсе, и дата в этом случае всё равно пустая.
Дата осталась в жёлтом предупреждении под плашками, которое и говорит про
выход за границы года.

Предупреждение это выглядит недостижимым — урок стоит внутри границ года,
значит и последний урок плана не может оказаться позже конца, — но
достижимо: **границы года правятся после**, а сужение проверяет только
разметку календаря, не расписание. Сдвинули конец года на май — уроки
остались в июне. Держит это `test_a_plan_can_end_past_the_end_of_the_year`,
и он там именно затем, чтобы предупреждение однажды не убрали как мёртвое.

**Дефицит на эти числа не влияет** — «осталось 30» значит тридцать уроков
плана, а хватит ли им дней, отдельный вопрос. У него своё предупреждение:
красным в шапке курса рядом с плашкой состояния, «4 урока не помещаются в
учебный год», вместо обычного «резерв: −4». Мелким текстом внизу это
сообщение потерялось бы. Цветом выделен только резерв, зелёным или красным: это
единственный показатель, у которого «плюс» и «минус» значат разное, и
единственный, где цвет — сообщение, а не оформление. Пока плашка была одна,
ряд читался как случайный набор чисел.

Подписи короткие намеренно: на плашке шириной в полтораста пикселей вторая
строка растягивает весь ряд, а в шапке курса резерв стоит числом со знаком
(«резерв: −28»), потому что смысл минуса проговаривает плашка состояния
справа. Ниже — какие темы разрослись, два ближайших урока и кнопки в план и
расписание.

Равенство высот держится не отступами, а тем, что в плашке ровно три
строки текста максимум; сторожит его `e2e/tests/progress-isolation.spec.js`
(«плашек четыре, и все одного роста») — он меряет курс с планом и курс без
плана, потому что расходятся плашки именно на пустых случаях.

**Что считается плохим.** Ровно одно: резерв `слоты − уроки`. Ноль и больше
— «в порядке», меньше нуля — «дефицит N уроков». Порогов и промежуточных
состояний нет. Отдельно, не влияя на плашку, показывается предупреждение,
если план кончается позже конца учебного года.

**Чего здесь больше нет и почему.** Разбивки по четвертям — дефицит бывает
только по году, а внутри заполненного терма баланс всегда ноль (см. выше).
Метрики темпа — при позиционной раскладке отставания не бывает по
построению: i-й урок лежит в i-м слоте, и пройдено всегда ровно столько
уроков, сколько прошло слотов; любая такая метрика была бы пересчётом
резерва, выданным за новость.

Всё приходит одним запросом `GET /api/plan/progress/`, который считает
числа тем же `build_layout`. Своих расчётов на странице нет вовсе — иначе
они однажды разойдутся с планом, как уже разошлись однажды учебные дни.

**Запросов у него шесть при любом числе курсов**: курсы, термы, план,
уроки, утверждённые эталоны и запросы на утверждение — все до цикла,
группировка по курсу в памяти. Было по шесть **на курс** (уроки, отмены,
план, термы, эталон и его строки), то есть тридцать семь на шести курсах —
для экрана, который открывают из бара. Расчёт при этом не менялся ни на
строку, поменялось только то, откуда ему приносят данные:
`services.lessons_by_course` и `approval.approved_baselines`/`open_requests`
— это те же одиночные выборки, сделанные разом.

Сторожит это `test_the_number_of_queries_does_not_grow_with_the_courses`, и
проверяет он не конкретное число — оно поедет от любой соседней правки, — а
то, что от числа курсов оно не зависит. Проверено поломкой: возвращённый в
цикл запрос эталона даёт 8 против 11.

Эндпоинты `/layout/` и `/layout/summary/` остались: ими пользуются тесты как
эталоном, с которым сверяется лента слотов (`test_it_agrees_with_the_layout`).

### Эталонный план и его утверждение

`PlanBaseline` — снимок структуры плана, `PlanBaselineRow` — его плоские
строки (позиция, `is_section`, название и `node_id`). Содержание и вложения
не копируются: эталон про структуру, а копия содержания удвоила бы хранение
ради вопроса, которого никто не задаёт. `node_id` хранится **числом**, а не
связью: узел могут удалить, и именно это удаление снимок должен пережить,
чтобы о нём рассказать.

**Снимок снимается в момент утверждения**: эталоном становится ровно то,
что приняли. Методист открывает **текущую** версию плана — правки после
отправки ничего не отзывают, запрос висит, пока его не обработают, и
утверждается то, что методист видит сейчас.

У самого плана состояния нет, учитель правит его свободно; состояние есть у
запроса: `pending`, `approved`, `returned`. Повторная отправка при висящем
запросе не заводит второй — обновляет дату и адресата, иначе очередь
методиста заполнилась бы одним и тем же курсом.

Снимков у плана несколько: утверждённый продолжает действовать, пока новый
лежит на утверждении, — иначе отправка новой версии стирала бы точку
отсчёта ровно тогда, когда она нужнее всего.

Вся процедура — `plans/approval.py`, и там же `notify`: писем пока нет,
хватает счётчика в баре, но событие есть, и когда рассылка понадобится,
добавлять её придётся в одно место, а не искать четыре перехода по вьюхам.

**Добавлено и удалено — две категории, а не сальдо** (`baseline_diff`). Обе
плохие, но по-разному: рост съедает резерв, удаление означает выкинутый
материал, и «плюс три минус три» тут не ноль, а шесть правок. Считается по
`node_id`, а не по названиям: переименованный урок остаётся тем же уроком.
По темам показывается только рост — дефицита по теме не бывает: тема, из
которой убрали урок, просто стала короче, а не «должна» его. Метрики
считаются **только от утверждённого** эталона: пока план не приняли,
сравнивать не с чем, и вместо чисел на экране приглашение отправить план.

### Методист

`schedule.CourseMethodist` — полномочие утверждать план **курса**, а не
ступень иерархии. Методист это тот же учитель со своими курсами и своим
планом; роль висит на паре «курс и человек», как и `CourseAssignment` рядом:
одна строка отвечает «кто ведёт», другая — «кто утверждает», и у одного
курса это обычно разные люди. Предмет школы — ярлык, а отвечают за
конкретный «9Б Алгебра», поэтому и назначают там же, где раздают курс.

- назначает **администратор школы** — «Школа → Курсы», в раскрытой строке
  курса блоком «Утверждает план» рядом с блоком «Ведут курс»
  (`/api/school/methodists/`, тот же вид, что у назначений);
- сам администратор ничего не утверждает, если его не назначили:
  администратор распоряжается школой, а не содержанием курса;
- **самоутверждение законно** — методист курса утверждает и свой план по
  нему, — но помечается: «утверждён автором»;
- методист видит запросы **по своим курсам**, а не только адресованные
  лично: методистов у курса бывает несколько, и прятать чужой запрос
  значило бы делать вид, что курс поделён между людьми;
- **править чужой план методист не может** — только утвердить или вернуть
  с замечанием, и замечание обязательно: возврат молчком это загадка.
  Правка чужого плана и не пройдёт: `TeacherScopedViewSet` отдаёт 404.

Раздел «На утверждение» (`/reviews`, `Reviews.jsx`) виден только тем, у кого
есть назначения: у большинства их нет, и пустой раздел в баре был бы
обещанием работы, которой нет. Рядом со ссылкой счётчик ожидающих — пока
единственное уведомление.

Отказ «плану некому идти» показывается **до** запроса: список методистов у
страницы уже есть, и получать ради этого 400 незачем. На сервере проверка
всё равно стоит — для тех, кто ходит в API мимо интерфейса.

## Первый вход

Разделы связаны по порядку: год → разметка календаря → классы → расписание →
план. Мастера с обязательным прохождением нет: он мешал бы при возврате и
правках. Вместо него — карта состояния.

`GET /api/onboarding/status/` отдаёт одним запросом, что уже заполнено: год
(самый свежий), число термов и исключений, классы с их счётчиками, слоты и
у скольких классов есть план. Всё считается по **текущему году** — на первом
входе других всё равно нет, а на главной иначе смешались бы прошлые.
В `classes.items` лежит сводка по каждому классу (слоты, прошло, осталось,
план, баланс) — чтобы главная не делала запрос на класс.

Главная (`Dashboard.jsx`) строит из этого список пяти шагов: выполненный
помечен галочкой и показывает сводку, первый невыполненный подсвечен как
«сейчас сюда», зависимый от невыполненного — приглушён и объясняет, чего не
хватает. Когда всё заполнено, список сменяется сводкой по классам, то есть
страница остаётся полезной.

В верхнем баре разделы без данных приглушены, причина — в подсказке. Клик
всё равно работает: жёстко запрещать переход незачем, страница сама покажет
пустое состояние (`EmptyState.jsx`) с объяснением и одной кнопкой.

`POST /api/onboarding/demo/` создаёт полный пример: год с каникулами и
четырьмя четвертями, два класса (у них разные дни недели, поэтому номера
уроков не конфликтуют), расписание на весь год мимо каникул и план на 44
урока у одного класса. `DELETE` сносит **все** данные пользователя —
помечать демо-объекты флагом ради этого не нужно, а подтверждение
спрашивает интерфейс. Обе операции в `transaction.atomic`.

Типовые каникулы предлагаются кнопкой на странице года, а не создаются
молча: даты у каждой школы свои. Одни и те же значения считают
`onboarding.services.typical_vacations` и `calendarLogic.suggestVacations` —
правьте оба места вместе.

## Боевая конфигурация

`docker-compose.prod.yml`, переменные в `.env.prod` (шаблон —
`.env.prod.example`; сам файл в проекте не лежит, см. ниже про три
env-файла). Первое развёртывание на сервер описано в
[DEPLOY.md](DEPLOY.md), последующие обновления — `./push-deploy.sh "текст
коммита"` с ноутбука: он коммитит, пушит, запускает `deploy.sh` на сервере
по ssh и проверяет, что сайт отвечает 200. Флаги: `--deploy-only` (только
раскатать), `--no-verify` (без проверки сайта) и `--skip-env` (не трогать
`.env.prod`). Перед стартом скрипт проверяет, что мы в корне репозитория, на
ветке `main` и что в рабочем дереве нет секретов — `git add -A` иначе
утащил бы их в коммит. На самом сервере всё то же делает `./deploy.sh`.

### Кто хозяин .env.prod

Главная копия — **на ноутбуке, вне репозитория**
(`~/secrets/lesson-tracker.env.prod`, путь меняется `DEPLOY_ENV_FILE`).
В git файл попасть не может, значит, на сервер он приезжает копированием, а
раз копирование одностороннее, у файла должен быть один хозяин: иначе
выкатка однажды затрёт правку, сделанную на сервере. Поэтому на сервере его
руками не редактируют, а `push-deploy.sh` отказывается работать, если
локальный файл лежит внутри репозитория.

Синхронизация идёт **до** `deploy.sh`: сборка фронта читает оттуда
`VITE_GOOGLE_CLIENT_ID`. Сравниваются sha256; при расхождении показываются
только **имена** появившихся и исчезнувших переменных — значения не
печатаются ни при каких обстоятельствах, там пароль базы и токены R2.
Дальше подтверждение, копия `.env.prod.bak.<дата>` на сервере (хранятся три,
и они в `.gitignore` — иначе `deploy.sh` счёл бы дерево грязным) и `chmod
600`. Нет локального файла — предупреждение и пропуск шага, а не отказ.

### Три env-файла и почему они разные

| файл | для чего | `DEBUG` | бакет R2 |
|---|---|---|---|
| `~/projects/lesson-tracker/.env` | разработка: runserver, Vite, `seed_demo` | `True` | dev |
| `~/secrets/lesson-tracker.env.local-prod` | прод-сборка на `http://localhost` | `False` | dev |
| `~/secrets/lesson-tracker.env.prod` | боевой; копия серверного | `False` | **прод** |

Совпадают у них только ключи Google: клиент один, `http://localhost` есть в
разрешённых origins. `SECRET_KEY`, пароль базы и токены R2 — разные, и это
не гигиена ради гигиены: `seed_demo --flush` чистит бакет целиком, поэтому
один запуск не с тем файлом стоил бы школе всех вложений. Отсюда правило:
**боевой бакет подключается только на сервере**, у локального прод-стека
dev-бакет.

Набор имён переменных у `local-prod` и боевого одинаковый — так видно, что
локальная проверка гоняет ту же конфигурацию, а не её огрызок. Различия
только в значениях: `localhost` в хостах и origins, `NGINX_SSL=false`,
выключенные secure-куки и HSTS (сертификата на localhost нет, а
`SECURE_SSL_REDIRECT` увёл бы проверку в https), пустые `R2_BACKUP_*` —
резерв локально не гоняем, и `backup_files` без них честно откажется
работать.

Прод-стек читает `env_file: .env.prod` и другого имени не знает, поэтому на
время проверки файл кладут в корень проекта копией, а потом убирают:

```bash
cp ~/secrets/lesson-tracker.env.local-prod .env.prod
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml down && rm .env.prod
```

Он поднимается рядом с dev — своё имя проекта, свои порты 80/443. В пустой
базе школы нет и войти некуда, поэтому в файле лежит закомментированная
пара `BOOTSTRAP_SUPERUSER_*`: раскомментировать — и будет доступ в
`/admin/`.

HTTPS включается одним флагом `NGINX_SSL=true` в `.env.prod`: `deploy.sh`
добавляет оверлей `docker-compose.ssl.yml`, который подменяет конфиг nginx
на `nginx/ssl.conf` и прокидывает `/etc/letsencrypt`. Конфиг с TLS —
отдельный файл, а не закомментированный блок, потому что правка
`nginx/default.conf` руками на сервере сломала бы `git pull` в `deploy.sh`.
Сертификаты выпускает certbot **на хосте** (`certonly --webroot`), продление
делает его systemd-таймер, а `scripts/reload-nginx.sh` в
`/etc/letsencrypt/renewal-hooks/deploy/` перечитывает конфиг в контейнере.

```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml logs -f backend
docker compose -f docker-compose.prod.yml down
```

Отличия от dev:

- backend — `gunicorn config.wsgi:application --workers 2`, стадия `prod`
  Dockerfile; код зашит в образ, bind-mount'а нет. При старте выполняются
  `migrate --noinput` и `collectstatic --noinput`.
- `db` не публикует порт наружу — до неё дотягивается только backend.
- `frontend-build` — одноразовый контейнер: `npm ci && npm run build`, кладёт
  бандл в том `frontend_dist` и завершается. nginx ждёт его через
  `condition: service_completed_successfully`.
- nginx раздаёт `frontend_dist` (с fallback на `index.html`) и `static_files`
  по `/static/`, проксирует `/api/` и `/admin/` на `backend:8000`.

Что стоит помнить:

- У prod-стека **своё имя проекта** (`name: lesson-tracker-prod`). Без него
  compose взял бы имя каталога — как у dev — и переиспользовал его контейнеры
  и том с базой. Благодаря разным именам оба стека можно держать поднятыми
  одновременно.
- Переменные в prod-compose приходят через `env_file: .env.prod`, а не через
  `${...}`: подстановка compose читает `.env`, которого в проде не будет.
  В healthcheck по той же причине `$$POSTGRES_USER` — разворачивает шелл
  контейнера, а не compose.
- `VITE_GOOGLE_CLIENT_ID` нужен **на этапе сборки** фронта: Vite вшивает его
  в бандл. Меняется — нужно пересобрать `frontend-build`.
- **Адрес backend'а nginx держит в переменной** (`set $backend_addr backend:8000;`
  плюс `resolver 127.0.0.11 valid=10s ipv6=off;`), а не в блоке `upstream`.
  Имя в `upstream` резолвится один раз при старте: после пересоздания
  контейнера backend получает новый IP, а nginx продолжает ходить на старый и
  отдаёт 502 до перезапуска. С переменной имя перечитывается по TTL. Обратная
  сторона — `proxy_pass` с переменной не делает подстановку URI, но у нас в
  `proxy_pass` и не было пути, так что запрос уходит без изменений.
- nginx объявлен `default_server`, поэтому отвечает на любой Host (это нужно
  для проверки по `http://localhost`). Django при этом свой `ALLOWED_HOSTS`
  проверяет: запрос к `/api/` с чужим Host получает 400.
- `manage.py check --deploy` на проде показывает **одно** предупреждение —
  `SECURE_HSTS_SECONDS`. Остальные три (`SECURE_SSL_REDIRECT`,
  `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`) читаются из env и включены
  с тех пор, как на сервере появились сертификаты. HSTS оставлен нулём
  сознательно: включается он легко, а выключается только по истечении срока
  у каждого браузера, который его запомнил.

## Фронтенд

`App.jsx` держит в `useState` токен (инициализируется из `localStorage`) и
решает только одно: есть токен — роутер и бар, нет — `Login`. Любая страница
при 401 от API сбрасывает токен и возвращает на логин.

### Ширина страницы

`.page` — 72rem, `.page.narrow` — 34rem, `.page.wide` — **88rem** (примерно
1400 px). Широкую берут страницы с таблицами и сетками: учебный план, моё
расписание, раскладка и школьное расписание. У плана до этого стояла
`narrow`, то есть 544 px: названия уроков обрезались многоточием посреди
слова, а справа оставалось пустое место. Дальше 88rem не идём — строка
становится слишком длинной, чтобы вести по ней глазами.

Остальные страницы остались как были: у справочников, школы и профиля
содержимое — формы и списки, которым ширина не нужна, а календарь и так
раскладывает месяцы сеткой.

### Карточки и вертикальный ритм

Расстояние между блоками задаёт **контейнер**, а не сами блоки. Три уровня,
все три объявлены переменными в начале `styles.css`:

| контейнер | шаг | что разделяет |
|---|---|---|
| `.page` | `--card-gap: 1rem` | карточки страницы |
| `.modal-body` | `--modal-gap: 0.75rem` | блоки внутри окна |
| `.panel` | `--panel-gap: 0.5rem` | заголовок, подсказка, форма, список внутри карточки |

У каждого из трёх прямые дети обнулены по вертикали (`> * { margin-top: 0;
margin-bottom: 0 }`). Это не косметика: собственные отступы блоков
складывались с gap, и один и тот же зазор оказывался то 1rem, то 2.5rem.
Кроме того, они односторонние — `.add-form` носила `margin-bottom`, и стоило
поставить форму **под** список, как она к нему прилипала.

До этого владельца отступа не было вовсе: `.panel` не нёс внешнего поля, и
две карточки подряд разделяло только то, что случайно оказывалось между
ними. Поэтому в «Справочниках» они стояли вплотную, а на «Обзоре школы»
четыре подряд сливались в одну колонку.

Карточек ровно два вида, и различаются они намеренно: карточка страницы
(`--card-radius: 8px`, `--card-shadow`) и строка внутри неё
(`--row-radius: 6px`, `--row-shadow` слабее) — иначе список внутри карточки
читался бы как десяток карточек. Литеральных радиусов и теней в файле не
осталось: новая карточка берёт переменную и попадает в систему сама.

Два исключения, оба осознанные: `.month` и `.week-grid` берут
`--card-pad-tight` (0.75rem) — это плотные сетки, где лишние 0.25rem съедают
колонку; `.step` на главной обведён рамкой вместо тени, потому что это
чек-лист, и текущий шаг обводится синим — поверх тени это читалось бы грязно.

### Строка формы

Всё про поля, селекты, кнопки и их выравнивание в ряду — **один блок** в
`styles.css`, помеченный «СТРОКА ФОРМЫ». Список контейнеров написан там один
раз, остальное — вложенные правила, поэтому разойтись с ним они не могут.
Правило для контрола в строке, написанное в другом месте файла, — ошибка:
раскладку здесь ломали трижды подряд, и каждый раз следующая правка чинила
один ряд и портила соседний.

- `--control-height: 2.25rem` — одна высота на поле, селект, кнопку и
  textarea. Мерили: поле выходило 36px, кнопка 39, селект без стилей 19 —
  три разные причины, порознь их подгонять бессмысленно.
- `min-height` у кнопки, жёсткая `height` у поля и селекта: кнопка с длинной
  подписью на узком экране переносится, а поле однострочно всегда, и без
  жёсткой высоты дата остаётся на 0.2px выше соседей.
- `white-space: nowrap`: от длины подписи кнопка становится шире, а не выше.
- Ряд переносится, только когда иначе вылезет за карточку, и ужимается
  сначала поле.

**Ловушка, на которой ломалось в последний раз:** поле с подписью
(`.field-with-hint`) — это колонка, и внутри неё `flex-basis` задаёт не
ширину, а высоту. `flex: 1 1 8rem`, написанное для ряда, растянуло поле до
128px. Поэтому растяжение адресовано только **прямым** детям ряда, а поле
внутри подписи явно снимает флекс.

Список контейнеров явный, а не «все кнопки»: кнопкой здесь бывает и клетка
календаря, и ячейка недельной сетки, и крестик в строке списка.

Сторожит это `e2e/tests/controls.spec.js` — обходит все ряды на всех
страницах в обеих локалях и меряет три вещи, которыми расходились прошлые
поломки: одинаковую высоту контролов, отсутствие переноса подписи и то, что
ряд не шире своей карточки. Проверено поломкой: возвращённое
`.add-form input { flex: 1 1 8rem }` валит его с текстом
«разная высота — input 128px, input 128px, button 36px».

### Навигация

Постоянный верхний бар `NavBar.jsx` (`position: sticky`), на страницах
никаких кнопок перехода нет — они дублировали бы бар. Выход и профиль живут
в меню пользователя справа; активный раздел подсвечен через `NavLink`
(заливка плюс подчёркивание). На узком экране пункты сворачиваются в
гамбургер: список открывается поверх содержимого и закрывается по выбору
пункта, клику мимо и Escape (общий хук `useDismissable`).

| Путь | Страница |
|---|---|
| `/` | главная: приветствие |
| `/schedule` | «Моё расписание» (`Agenda.jsx`) |
| `/status` | «Состояние курсов» |
| `/plan` | «Учебный план» |
| `/reviews` | «На утверждение» — только для методистов |
| `/classes` | «Классы» |
| `/year` | «Учебный год» (`Calendar.jsx`) |
| `/profile` | профиль |
| `*` | «страница не найдена» со ссылкой на главную |

Имя в баре берётся одним запросом `/api/me/` в `App.jsx` и обновляется сразу
после сохранения профиля (`onSaved`), чтобы не перечитывать его на каждой
странице.

Прямой заход по адресу работает: Vite в dev отдаёт `index.html` на любой
путь, в проде это делает `try_files $uri /index.html` в `nginx/default.conf`
(проверено на реальном nginx с этим конфигом — `/plan`, `/classes`,
`/nope/deep` возвращают `index.html`, а существующие файлы отдаются как есть;
`/api/`, `/admin/` и `/static/` перехватываются своими location до fallback).

Имя и фамилию при первом входе заполняет allauth при регистрации, а для уже
существующих аккаунтов — обработчик сигнала `user_logged_in` в
`accounts/signals.py`. Заполненные значения он не перезаписывает: иначе вход
через Google затирал бы то, что пользователь поправил в профиле.

Запросы идут на относительный `/api/...` — в dev их проксирует Vite, так что
CORS в разработке фактически не задействован (настройки всё равно нужны для
прода, где фронт и API будут на разных origin).
